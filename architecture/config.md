# Configuration

How one process turns flags, environment variables and defaults into a validated `config`, and how that becomes the `ServiceConfig`, the storage identity and the S3 or hosted store settings. It answers "where does `--bucket` (or `--space`, or any other setting) come from, what is its default, and what makes startup refuse it?"

Read this when: adding or changing a flag or environment variable, changing a default or bound, touching the ephemeral session directory, the shared pack cache root, endpoint normalization, the read-only/writable path sets, S3 credentials, the hosted-mode token and space ([hosted-mode.md](./hosted-mode.md)), or `--storage` and stored logins ([login.md](./login.md)).

## Flow

```text
cmd/<serve|pull|commit|status|log>.Command: flags := app.NewFlags(); flags.Bind(fs)
router parses fs
app.Setup(engine, flags, opts) → setup(process)
  → loadConfig(p)                                   # parses p.args only when p.flags == nil
    → Flags.resolve(env, cwd, cacheDir, ephemeral, newSessionDir, association)
        environ(env) → resolveString/Bool/Int/Root per setting
        roots resolve first, so an omitted path is the workspace root
          and that root is the record key; a session directory skips the record
        settingsAssociation.read → settingsView{record, recorded, S3 default}
        resolveStorage(flags, env, {runtime.GOOS, time.Now(), remembered})   # login.md
          --storage | SLIVINGDOC_STORAGE | auto; bucket: --space | --bucket |
            SLIVINGDOC_SPACE | SLIVINGDOC_BUCKET (resolveBucket: two spellings
            of one layer that differ are a refusal naming both)
          kind: s3 | hosted | auto
            auto: SLIVINGDOC_TOKEN → hosted; a bucket spelling beside S3 signals → S3;
                  the record's kind → that kind; the S3 default → S3;
                  a usable stored login → hosted; else S3
          s3: each field flag/variable → a record of kind s3 → the S3 default →
              ambient AWS; a --space | SLIVINGDOC_SPACE name beside an S3 record
              or default is a refusal; --space alone names a bucket
          hosted: the login's endpoint; name flag/variable → hosted record →
                  login default space; prefix flag/variable → hosted record
        ephemeral && no root set → newSessionDir() → <session>/notebook, <session>/private
        cacheDir known → packCacheRoot = <cacheDir>/slivingdoc/pack-cache (else private cache)
        --log-level set → slogcolor.ParseLevels (fail fast)
      → config.finish(cwd)
          bucket required (optional with a token), ValidatePrefix, normalizeEndpoint,
          a named prefix that contradicts the record is a refusal,
          hosted ? validateHosted (space, token, https unless loopback) : no region requirement
          (an empty S3 region is legal; the adapter falls back to us-east-1),
          absolute(roots), RootsOverlap (refuses the private root, falls back
          for the pack-cache root), numeric bounds, resolvePolicy
  → buildService → realStoreFactory
        hosted ? httpstore.New(Config{Endpoint, Space: Bucket, Prefix, Token, UserAgent})
               : s3store.New(Config{Bucket, Prefix, Region, Profile, Endpoint},
                             Options{ForcePathStyle})
  → config.withStoreResolution(store): Store.Resolved() supplies the effective
        endpoint, region, profile and path style before the probe proof,
        the notebook identity and the record
  → config.serviceConfig() → NewService
```

## Behavior

**Settings table.** `serve`, `pull` and `commit` share every setting through `app.Flags`; `commit` adds `-m`/`--message`. `FlagReference` in `config.go` is the authoritative help text printed by `-h`.

| Setting | Flag | Environment | Default | Validation (`finish` unless noted) |
|---|---|---|---|---|
| Storage backend | `--storage` | `SLIVINGDOC_STORAGE` | `auto` | `auto`, `hosted` or `s3` (`parseStorageMode`); the selection rules are in [login.md](./login.md) |
| Hosted API token | none | `SLIVINGDOC_TOKEN` | empty (a stored login, else S3 mode) | hosted: `httpstore.ValidateToken`; ignored with `--storage s3` |
| Credentials directory | none | `SLIVINGDOC_CONFIG_DIR` | `<user-config-dir>/slivingdoc` | absolute (`credentials.Locate`); the file is read strictly, up to 1 MiB, unless `--storage s3` or `SLIVINGDOC_TOKEN` is set; a symbolic link, a non-regular file, and (not on Windows) a file or directory another user owns, a file other users can read or write, or a directory they can write, are refused (`credentials.ErrExposed`); `login` refuses such a directory even without the file; `login`, `logout` and `space <name>` write it under `credentials.lock`; a file of any version but 2 is refused by every command that reads it, `login` included (`credentials.ErrUnsupportedVersion`: an older one is to be removed, a newer build's kept and slivingdoc updated) |
| Scoped settings file | none | none | none | a directory's remembered target and the one global S3 default: read by `pull`, `commit`, `status`, `log`, a durable `serve` and `space` except in create mode; `space` reads it for its directory column and the active default it marks. A successful `pull`, `commit` or durable-server tool call writes it; it lives at `<credentials directory>/workspaces.json`, is read strictly up to 1 MiB with the credentials file's own refusals (`internal/settings`, `settings.ErrExposed`, `settings.ErrUnsupportedVersion`), and is written under `workspaces.lock`. A scratch `serve` and `space` create mode neither read nor write it |
| Bucket (hosted: space) | `--bucket`, or its hosted name `--space` | `SLIVINGDOC_BUCKET`, or its hosted name `SLIVINGDOC_SPACE` | S3: the directory record, then the S3 default; neither → none (required). Hosted: the token's space, else the directory record, else the login's default space (`slivingdoc space <name>`) | required in S3 mode; both spellings of one layer with different values are refused; hosted: optional, `httpstore.ValidateSpace` when given, must equal the token's space, or be one the login reaches (the site checks it when it mints) |
| Prefix | `--prefix` | `SLIVINGDOC_PREFIX` | `slivingdoc`, after a record of the resolved kind, then the S3 default | `storage.ValidatePrefix`; a named prefix that contradicts the record is refused |
| Region | `--region` | `AWS_REGION`, then `AWS_DEFAULT_REGION` | empty, after a record of the resolved kind, then the S3 default (the profile's region, else `us-east-1` in the adapter) | not resolved when hosted; an empty value is legal and the adapter applies `us-east-1` |
| Profile | `--profile` | `AWS_PROFILE` | empty, after a record of the resolved kind, then the S3 default (the ambient chain) | a selector, never a secret; unused when hosted |
| Endpoint | `--endpoint` | `AWS_ENDPOINT_URL_S3`; hosted: `SLIVINGDOC_ENDPOINT` | empty, after a record of the resolved kind, then the S3 default (AWS resolution); hosted: `DefaultHostedEndpoint` (`https://api.slivingdoc.dev`) | `normalizeEndpoint`; hosted: `https` unless loopback |
| Path style | `--path-style` | `SLIVINGDOC_PATH_STYLE` | `false`, after a record of the resolved kind, then the S3 default | `strconv.ParseBool`; unused when hosted |

| Private root | `--private-root` | `SLIVINGDOC_PRIVATE_ROOT` | serve with neither root configured: `<session>/private`; otherwise `<user-cache-dir>/slivingdoc` | not at or below workspace root |
| Commit retries | `--commit-retries` | `SLIVINGDOC_COMMIT_RETRIES` | 8 | 0..100 |
| Checkpoint packs | `--checkpoint-packs` | `SLIVINGDOC_CHECKPOINT_PACKS` | 256 | at least 1 |
| Retained checkpoints | `--retained-checkpoints` | `SLIVINGDOC_RETAINED_CHECKPOINTS` | 1 | 0..64 |
| Read-only paths | `--read-only-paths` | `SLIVINGDOC_READ_ONLY_PATHS` | none | `resolvePolicy` |
| Writable paths | `--writable-paths` | `SLIVINGDOC_WRITABLE_PATHS` | none | `resolvePolicy` |
| Ignore patterns | `--ignore` | `SLIVINGDOC_IGNORE` | none, on top of `workspace.DefaultIgnore` | comma-separated (`splitPathEntries`); `workspace.NewIgnore` in `finish` |
| Log level | `--log-level` | `LOG_LEVEL` | info | flag: `slogcolor.ParseLevels`, fatal; env: lenient |

Not flags: `NO_COLOR` and `DEBUG_PERF` are read from the environment only ([logging.md](./logging.md), [cli.md](./cli.md)), and so are the two encryption settings `SLIVINGDOC_PASSPHRASE` and `SLIVINGDOC_PASSPHRASE_FILE`, which no command-line flag can name ([encryption.md](./encryption.md)).

**Precedence.** An explicitly set flag wins over the environment, which wins over the default (`resolveString`, `resolveBool`, `resolveInt`); exception: the S3 transport endpoint, see Gotchas. Each flag type records `set`, so an explicitly empty flag (`--read-only-paths=`) does not fall back to the environment; that is how a process clears an inherited value. An empty environment value counts as unset. For roots, an explicitly empty flag counts as configured and then fails the empty-root check (`resolveRoot`, `absolute`). A duplicated environment variable takes its last value (`environ`).

**Value grammar.** Booleans use `strconv.ParseBool` (`boolFlag` also accepts the bare form: `--path-style`, `--log-timestamp`). Integers are unsigned decimal only: `parseUnsigned` rejects any sign or non-digit and bounds the value to 31 bits. Path-set values are comma-separated, trimmed, and empty pieces dropped (`splitPathEntries`).

**Bucket, prefix, endpoint.** `--bucket` names the S3 bucket; slivingdoc never creates or configures it. `--space` and `SLIVINGDOC_SPACE` are the same setting under its hosted name ([login.md](./login.md)): a flag beats the variables, an explicitly empty flag does not fall back, and `--bucket` and `--space` (or the two variables) with different values refuse startup naming both. `--prefix` is empty or a slash-separated relative key prefix with no leading or trailing slash, empty segment, backslash, `.` or `..` segment (`ValidatePrefix`); one prefix holds one notebook, and the adapter joins it to protocol keys ([storage.md](./storage.md)). `--endpoint` must be an absolute `http`/`https` URL without user information, query or fragment; `normalizeEndpoint` lowercases scheme and host, removes trailing slashes and keeps a non-root path, and refuses a value whose normalized form does not parse again (a non-ASCII IPv6 zone), so a stored endpoint always loads. A custom endpoint always uses path-style addressing; `--path-style` extends that to the default AWS endpoint (`s3store.New`).

**Hosted mode.** `resolveStorage` picks the token ([login.md](./login.md)): a non-empty `SLIVINGDOC_TOKEN` unless `--storage s3`, else a usable stored login unless `--storage s3`: the one for an explicit endpoint, else the only one, with the space setting, else the space a hosted record of this directory names, else the endpoint's stored default space. A record selects its own kind, so only a hosted record reaches this paragraph; an S3 record selects S3 with its own fields. Under `auto`, a variable token always selects hosted mode and takes precedence over S3 settings and the record; `--storage s3` is the explicit override. A stored login for a space named as `--space` or `SLIVINGDOC_SPACE` beside an S3 signal is refused until `--storage hosted` or `--storage s3` chooses, while the same space named as `--bucket` or `SLIVINGDOC_BUCKET` selects S3, because that spelling names a bucket (`bucketSource.namedAsBucket`); a login whose space is the stored default, or the space the directory remembers, wins over S3 signals, since S3 would have no bucket. The signals are the AWS variables, `AWS_CONTAINER_CREDENTIALS_*`, `SLIVINGDOC_PATH_STYLE`, the `--profile`, `--region` and `--path-style` flags, and an existing `~/.aws/credentials` or `~/.aws/config` (`s3Signals`, the exact table in login.md). `setup` logs the outcome at Info (`logStorage`). A stored login's key is sent only to the site that issued it (to list spaces, mint tokens and be revoked); the process mints short-lived tokens of the space (`mintedTokens`, `config.tokens`) and sends them only to the login's endpoint. A token or a login makes `config.hosted` true, `config.tokenOrigin` records where it came from and `config.bucketFrom` which setting named the bucket, in the spelling used: `--space`, `--bucket`, `SLIVINGDOC_SPACE`, `SLIVINGDOC_BUCKET`, the stored default space, the remembered space or the token. The bucket is then optional for `SLIVINGDOC_TOKEN` and, when present, names the hosted space; `buildService` fills an empty one with the token's own space and refuses one the token does not reach, worded for its source (`resolveHostedSpace`, `spaceMismatch`, [hosted-mode.md](./hosted-mode.md)). The endpoint resolves from `--endpoint`, `SLIVINGDOC_ENDPOINT`, then `DefaultHostedEndpoint` for the variable's token, and is the login's own endpoint for a stored login (an explicit endpoint that differs means the login does not apply), and `AWS_REGION`/`AWS_ENDPOINT_URL_S3` are not read (the region stays empty and is not required). After `normalizeEndpoint`, `validateHosted` refuses a given space outside the `httpstore.ValidateSpace` grammar, a `SLIVINGDOC_TOKEN` that is not printable ASCII without white space (the message names `SLIVINGDOC_TOKEN`, never its value), and a non-`https` endpoint unless its host is loopback (`httpstore.IsLoopback`). See [hosted-mode.md](./hosted-mode.md).

**Storage identity.** `Service.identity` builds `workspace.Identity{Endpoint, Region, Bucket, Prefix, ManifestVersion, SpaceID}` from the normalized values (in hosted mode: the hosted endpoint, an empty region, the space, and the server's id of that space, `config.spaceID`, when the server names one; the token is not part of it). The endpoint, region and path style are the effective values a built S3 store reports (`config.withStoreResolution`), so a profile-supplied region selects the identity the store really addresses; the profile itself is configuration and is not part of the identity or the probe proof. `DerivedKey` hashes it with the canonical visible path to name the private directory, and `SharedCacheDirName` hashes it without the path to name the shared cache directory. Changing the endpoint spelling, region, bucket or prefix, or reaching another hosted space of the same name, therefore selects different private state.

**Credentials.** No flag carries a credential. The only credentials slivingdoc reads itself are the hosted API token from `SLIVINGDOC_TOKEN` and the account key in the credentials file that `slivingdoc login` writes ([login.md](./login.md)); a token, the variable's or one minted from the key, travels only in the hosted adapter's `Authorization` header, and the key only to its site ([hosted-mode.md](./hosted-mode.md)). In S3 mode `realStoreFactory` leaves `s3store.Config.AccessKey`/`SecretKey` empty, so `awsconfig.LoadDefaultConfig` uses the AWS SDK default chain: `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`, the shared files with `--profile` or `AWS_PROFILE`, then ambient identity (SSO, ECS/EKS task roles, EC2 metadata). `AccessKey`/`SecretKey` are set only by tests (`tests3.Suite.StoreConfig`). An endpoint with user information is refused, so a secret cannot echo into a diagnostic. The operator view is in [running.md, S3 credentials](./running.md#s3-credentials).

**The configuration directory.** `credentials.ConfigDir` is the one rule that resolves the directory the slivingdoc configuration files live in: `SLIVINGDOC_CONFIG_DIR` when it is set and absolute, else the platform's user configuration directory plus `slivingdoc`, read through an injected environment so a test never touches the developer's own directory. A directory that does not resolve is a `NoConfigDir` naming the cause, which `NoDirectory` words in the calling package's own vocabulary. `credentials.Locate` and `settings.Locate` call it, so both files are always beside each other.

**The hardened configuration file.** Every slivingdoc configuration file is read and written through `credentials.PrivateFile`: `Read` refuses a symbolic link, anything but a regular file, and (not on Windows) a file or directory another user owns, a file others can read or write or a directory they can write, and reads at most `MaxBytes`; `CheckDir` is the same directory rule alone; `Write` creates the directory 0700, writes a temporary file 0600 in it, syncs it and renames it over the file; `Lock` takes an advisory lock beside the file. The schema and the error wording belong to the package that owns the file, which passes them as `Wording`. `credentials.json` and `workspaces.json` differ in nothing but that.

**The scoped settings store.** `internal/settings` holds one file, `workspaces.json`, mapping a directory to the notebook it holds and holding the one global S3 default. A record names a `Target` of `{Kind, Endpoint, Region, Profile, Name, Prefix, PathStyle}`: `Kind` is `hosted` or `s3`, `Name` is the hosted space or the S3 bucket, `Endpoint` and `Region` are the effective store values with an empty one meaning the provider default, `Profile` is the AWS shared-config selector (a name, never a secret), and `PathStyle` is the effective addressing mode. A hosted target leaves `Region`, `Profile` and `PathStyle` empty and keeps an empty `Endpoint`, because the selected login supplies the site. A `hosted` target in `defaults` is malformed, because a hosted default lives in `credentials.json` and two sources must not disagree. The stored S3 default is the active global default while one exists, and a bare `space` listing resolves its identity when no S3 flag or variable names one; a hosted selection stores no S3 default, so the selected login's default space is then active ([login.md](./login.md)). The record names no credential: the schema has the target's backend fields only, so a token or a key beside them is an unknown field and the whole file is `ErrMalformed`.

The format is version 2. The encoder writes `version`, `entries`, `defaults` in that order, with `defaults` an empty array when none is stored, and a target's fields in the order `kind`, `endpoint`, `region`, `profile`, `name`, `prefix`, `pathStyle`. The decoder dispatches on `version`: version 1 is read through its own path, where `{space, prefix}` becomes `{Kind: hosted, Endpoint: "", Name: space, Prefix: prefix}`, so an existing short hosted space keeps working and reading rewrites nothing; version 2 is the shape above; any other version is `ErrUnsupportedVersion`, read no further and never rewritten. The next `Save` always writes version 2. `Locate` follows the configuration directory rule, `Load` is strict (`strictjson`, 1 MiB, an unknown, duplicate, missing or null field refused, a name or path that is empty refused, a prefix outside `storage.ValidatePrefix` refused, a hosted target that names an S3 field refused, and two entries for one path refused), and `Save` is the hardened write. `Set.Put` is pure and replaces an entry in place, so a rewrite neither moves it nor loses another writer's entry; `Set.PutDefault` stores one target as the only default and `Set.ClearDefaults` stores none, while `Set.S3Default` returns the last stored default, or none, so a version-2 file written by the earlier per-store-key build keeps working until the next default write collapses it to one. `Target.Key()` is `{Kind, Endpoint, Region, Profile}`, the identity a listing group dedupes on and not the name or the prefix; the read-modify-write belongs to the caller, under `File.Lock` (`workspaces.lock`, which is its own lock file, so the two configuration locks never wait for each other). `Config` injects the bound and the reader for a test.

**The remembered target of a directory.** Every command that addresses a notebook directory consults the scoped settings: `pull`, `commit`, `status` and `log` set the association of their resolved path (`ProcessOptions.WithAssociation(path)`), and `serve` sets it for its workspace root, so a durable directory reads and records one; a scratch directory sets none, because it does not survive the process (I8). `space` reads the whole scoped settings set (`spaceSettings`, over the same `scopedSettings` reader or an injected `ProcessOptions.Load`) to print the directories beside each target and to read the active global default it marks, which is also the identity a bare listing resolves when no S3 flag or variable names one: a record never selects its own target. The reader (`scopedSettings`) locates the file by the configuration directory rule and reads it once per process, and `settingsAssociation.read` looks the record up by the resolved notebook path, or by the workspace root when the command gave none: an omitted path is that root, which is why `Flags.resolve` resolves the roots before `resolveStorage` (`resolveRoots`). Symlinks are never resolved and the key is byte-bound, so two spellings of one directory are two records. A file that cannot be read is a refusal naming the file and the way to run without it (`unusableSettings`), never an empty set.

`resolveStorage` resolves the backend first (`selectKind`): `--storage s3` or `SLIVINGDOC_STORAGE=s3` selects S3 and ignores `SLIVINGDOC_TOKEN`; otherwise the token selects hosted; otherwise `--storage hosted` or `SLIVINGDOC_STORAGE=hosted` selects hosted; otherwise, in `auto`, a `--bucket` or `SLIVINGDOC_BUCKET` name beside an S3 signal selects S3; otherwise the kind the directory records; otherwise the one global S3 default selects S3; otherwise a usable stored login selects hosted; otherwise S3. The shipped `--space`/login rules fill the remaining cases: a `--space` or `SLIVINGDOC_SPACE` name beside an S3 record or the S3 default keeps its ambiguity refusal, while with neither that spelling names an S3 bucket, because a store without a hosted alternative has no second meaning. Each field then resolves from its flag or slivingdoc variable, then a record of the resolved kind, then the global default of that kind, then the ambient configuration (`resolveS3Target` for S3; `resolveHostedTarget` supplies the name and prefix and takes the endpoint from the selected login): the name, prefix, profile, endpoint, region and path style in the order the settings table states. A record of another kind supplies no field, so `--storage s3` beside a hosted record and `--storage hosted` beside an S3 record each resolve from that run's own settings. A hosted record with no endpoint uses the selected login's endpoint, and a hosted target with no credential is `noCredentialRefusal`, naming the space rather than reading it as an S3 bucket. `resolveTargetPrefix` refuses a named prefix that contradicts the record with `prefixMismatch`, because the record says which notebook of the store this directory holds.

After the store is built, `config.withStoreResolution` applies the effective endpoint, region, profile and path style a store reports through `resolvedStore` (`s3store.Store.Resolved`): a profile or the SDK may have supplied a region or an endpoint after the configuration resolved, and the probe proof, the notebook identity and the record must name the store the process really uses. The profile is configuration and reaches neither the identity nor the proof. A record's profile can therefore change the effect of a later run: a region no flag or variable named changes the identity once, and the first operation under that profile builds fresh private state and imports the notebook's packs again. No note is lost, because `current` is the only accepted-state authority. A store that reports none, such as an injected fake, leaves the resolution-time values.

**Recording the association.** A successful `pull`, a successful `commit`, or a successful tool call of a durable `serve` records the complete target it proved the directory holds (`Runtime.rememberSpace`, called from `Runtime.Pull` and `Runtime.Commit` and from `rememberingService` around the served operations). It records `config.target()` under the same key the record is read by, never a credential: a hosted target names the space and prefix, because the selected login supplies the site, while an S3 target names the effective endpoint, region, profile, bucket, prefix and path style. The gate is `Runtime.recordEntry`: the process carries an association, it does not own a session directory, the directory remembers nothing, no `SLIVINGDOC_TOKEN` is set, and the name came from a flag or a slivingdoc variable. The login's default space, the global S3 default and the token's own space are never recorded — the defaults because changing them must keep working everywhere, the token because it names its space for one run and ignores the record (D11) — and a flag or a variable records only where the directory remembers nothing, because what a directory remembers is the target it already holds (I3, I6, I7, I8). `rememberSettings` locates the file by the configuration directory rule and `storeEntry` writes it as a read-modify-write under `workspaces.lock`; an entry that already says this is left byte for byte, so a repeated operation never rewrites the file. A failed operation proves nothing about the target and records nothing. A write that cannot happen, including a file this build cannot read or one over the bound, logs one warning at the `notebook` level and changes neither the result nor the exit code: the record is a convenience beside the operation, never a part of it.

**The operator surface of the record.** The order is stated once, in the paragraph `FlagReference` ends with, so every command that embeds it prints it (`-h` returns before any dependency loads): the flags, then the slivingdoc variables, then the target the notebook directory remembers, then the one global default (the stored S3 default, else the login's default space), then the ambient AWS configuration, and the file the record and the default live in. Each of `pull`, `commit`, `status` and `log` adds one sentence of its own about a directory that needs no target flag, and `serve` adds the durable/scratch distinction. `status` passes the resolved source to `ReportStatus`, which adds a dimmed trailer below the path line only for a source the directory supplied: `space: remembered space` for a hosted record and `bucket: remembered bucket` for an S3 record. A source the operator set by hand needs no explanation, and a global default has no trailer either; `log` has no line that could carry a source, so it names none. The trailer is rendered through the same `tui.Detect` style as every other line, so a pipe and `NO_COLOR` see plain words ([tui.md](./tui.md)).

**Ephemeral session directory.** When `ProcessOptions.Ephemeral` is set (only `serve`) and neither root is configured, `resolve` calls `NewSessionDir` (default `os.MkdirTemp("", "slivingdoc-")`) and uses `<session>/notebook` and `<session>/private`. The random component keeps two servers apart; the durable notebook is the bucket. `Runtime.Close` removes the whole directory, and a refusal after creation removes it too. Configuring either root disables this: the workspace root then defaults to the startup cwd and the private root to `<user-cache-dir>/slivingdoc`, and neither is removed. `pull` and `commit` never take a session directory.

**Roots.** Both roots and the pack-cache root become absolute and clean (`absolute`: `~` or `~/` expansion, then join to cwd). Without a resolvable user cache directory the private-root default degrades to `<cwd>/slivingdoc`, which overlaps a cwd workspace root and refuses startup; set `--private-root`. The private root must not be at or below the workspace root, while a shared pack-cache root in that position falls back to the private cache (`workspace.RootsOverlap`), because private state inside a visible directory would become notebook content. `workspace.Open` re-checks both.

**Shared pack cache.** Always on: `packCacheRoot` is `<cacheDir>/slivingdoc/pack-cache`, and each notebook identity gets `<sanitized bucket>-<sanitized prefix>-<16 hex of the identity digest>` below it (`SharedCacheDirName`; `sanitizeCacheComponent` lowercases, maps every non-`[a-z0-9]` to `-`, and truncates each part to 32). There is no flag. Two cases keep the private per-workspace cache instead (`packCacheRoot` empty, `packCacheMode` says why, `setup` logs it at debug): no resolvable user cache directory (`packCacheNoUserDir`), and a shared directory at or below the workspace root, where it would become notebook content (`packCacheBelowWorkspace`, decided in `config.finish` with `RootsOverlap`). The same identity directory holds the recorded store compatibility proof `probe-ok.json` that lets a later process skip the startup probe (`config.probeProofs`, [storage.md](./storage.md)); without a shared cache there is no proof. See [workspace.md](./workspace.md).

**Numeric bounds.** `--commit-retries` counts retries after the first CAS attempt; exhaustion is `REMOTE_BUSY`. Retry delay uses full jitter from an exponential ceiling starting at 25 ms, capped at 2 s (`notebook.defaultBackoffMin`/`defaultBackoffMax`). `--checkpoint-packs` is the active tail length that schedules a checkpoint; `--retained-checkpoints` is how many previous checkpoint generations the manifest keeps ([checkpoints.md](./checkpoints.md)). The bounds are the notebook's constants, so flag and notebook validation cannot drift.

**Path sets.** `resolvePolicy` first normalizes the read-only entries (`git.NormalizeEntries`), then composes both with `git.NewPolicy`. An invalid entry refuses startup naming the setting; a path named by both settings is an `OverlapError` rendered as `--read-only-paths "x" and --writable-paths "x" name the same path`. `finish` stores `policy.ReadOnly()`/`Writable()` back into the config. The sets resolve by longest match, and a non-empty writable set protects every unmatched path; the behavioral contract is in [running.md, Read-only paths](./running.md#read-only-paths).

**Notebook encryption key material.** The encryption commands read the candidate secrets of this notebook identity from two settings and one file, never from a flag: `SLIVINGDOC_PASSPHRASE` (the plaintext secret itself), `SLIVINGDOC_PASSPHRASE_FILE` (the path of an envfile that holds it), and the key record. The record is `notebooks.json` in the same configuration directory as `credentials.json` and `workspaces.json` (the configuration directory rule below), a strict versioned file (`keyrecord.FormatVersion` 1) that maps the lowercase SHA-256 identity digest (`workspace.IdentityDigest`) to one entry: a stored passphrase or the path of an envfile. It is read and written through the same hardened `credentials.PrivateFile` as every other configuration file, and a change is a locked read-modify-write under `notebooks.lock`. A refusal from either setting names the setting (`SLIVINGDOC_PASSPHRASE_FILE` or `passphraseFile`) and never the path; the settings' values and the record are never logged or echoed. The file is read only by the `encrypt` commands and by a process that holds the notebook key material, and it is the only configuration file that can carry a plaintext secret, which `--store-passphrase --confirm-store-passphrase` acknowledges ([encryption.md](./encryption.md)).

**Diagnostics.** Resolution and validation refusals (environment values, `--log-level`, everything in `finish`) are wrapped by `setup` as `app: invalid configuration: <msg>` and passed through `mcp.Redact`. A malformed flag value on the command line is rejected earlier by the flag parser, unredacted: by the router (one stderr line `error: <command>: <flag error>; run 'slivingdoc <command> -h' for its flags`, empty stdout) when it precedes the path, or by `OperationPath` (`pull: ...`, `commit: ...`) when it follows it. Messages never echo credentials or private values; path-set entries are notebook-relative and may be named.

## Gotchas

- `ServiceConfig` mirrors the storage, root, numeric and path-set fields of `config` but not all of them: it has no token (nor the session directory or logging fields), so a `ProcessOptions.StoreFactory` never sees hosted mode, and the hosted process scenarios use helper mode `real` (no injected factory). A new setting that the service or store factory needs must be added to `config`, `ServiceConfig`, and `serviceConfig()`; `integrationtest/itest.NewHarness` builds `ServiceConfig` directly and must be updated too.
- Adding a flag means: a field on `Flags`, a line in `Bind`, a resolve call in `resolve` (or `resolveStorage`), validation in `finish`, and a row in `FlagReference`. `TestReleaseBinaryCommandSurface` and the `serve -h` scenario assert the help text; `TestHelpTextNamesTheOrder` asserts the paragraph after the table.
- `SLIVINGDOC_LOG_TIMESTAMP` alone sets `logConfigured`, which makes `setup` rebuild the logger; `LOG_LEVEL` alone does not (the environment logger already honours it).
- `--endpoint` is shared by both modes: with `SLIVINGDOC_TOKEN` set, `--storage auto` selects hosted mode and the flag names its hosted endpoint; AWS endpoint variables are ignored. `--storage s3` explicitly selects S3 and never reads the token. `SLIVINGDOC_ENDPOINT` names the hosted API. A stored login is only used for the endpoint it was issued for, and several logins need `--endpoint` or `SLIVINGDOC_ENDPOINT` to choose one.
- The region flag has an empty default, so only an explicitly set `--region` (or `AWS_REGION`, `AWS_DEFAULT_REGION`) is an S3 signal; `--profile` and `--path-style` are signals the same way. They count only against a stored login for a space named as `--space` or `SLIVINGDOC_SPACE`, never against `SLIVINGDOC_TOKEN` and never against the `--bucket` spelling.
- `resolveStorage` normalizes an explicit `--endpoint`/`SLIVINGDOC_ENDPOINT` even when the process ends up in S3 mode, so a malformed `SLIVINGDOC_ENDPOINT` now refuses startup outside `--storage s3`. The credentials file is read through the injected environment only; `testProcess` passes no `HOME`, so unit tests see no logins unless they set `SLIVINGDOC_CONFIG_DIR`.
- The region resolves as `--region`, then `AWS_REGION`, then `AWS_DEFAULT_REGION`, then the selected profile's `region`, then `us-east-1` in `s3store.New`. An empty configured region passes no `WithRegion`, so the SDK loads the profile's region, and the adapter applies the default only when that is still empty. `s3store.Resolve` reports the region as loaded, which may be empty; `Store.Resolved().Region` never is. `--profile` (or `AWS_PROFILE`) selects the shared-config section (`WithSharedConfigProfile`) and is never a credential. `AWS_ENDPOINT_URL_S3` is read by slivingdoc (in S3 mode only) and passed explicitly (`WithBaseEndpoint`). The S3 client resolves its service endpoint again in `resolveBaseEndpoint`, over the load options first, then the environment, then the shared profile; so a non-empty `--endpoint` wins over `AWS_ENDPOINT_URL_S3` and a profile's `services` s3 `endpoint_url`. `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true` or a profile's `ignore_configured_endpoint_urls = true` makes the configuration load drop every configured endpoint, `WithBaseEndpoint` included, which would send the traffic to AWS; `s3store.New` therefore also sets `BaseEndpoint` on the S3 client options, after the load, whenever an endpoint is configured. `TestConfiguredEndpointBeatsServiceEndpointSettings` covers all four settings, with negative-control rows showing that without an endpoint the ambient settings do redirect. An empty endpoint passes no load option, so `--endpoint=` does not clear a process `AWS_ENDPOINT_URL_S3`, and a generic `AWS_ENDPOINT_URL` or a profile `endpoint_url` redirects traffic without entering the storage identity or forcing path style. Other `AWS_*` variables reach the SDK only through `LoadDefaultConfig`.
