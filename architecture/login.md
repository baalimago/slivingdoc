# Login, stored credentials, and storage selection

`slivingdoc login` logs in to a hosted account through a browser approval (the device flow, like `gh auth login`) and stores the account's CLI key, so `serve`, `pull` and `commit` reach a hosted space without `SLIVINGDOC_TOKEN`. The key never reaches storage: a process trades it at the site for a short-lived token of one space, held in memory only. `slivingdoc space` lists the spaces the login reaches and sets the default one. `slivingdoc logout` revokes the key, and with it every token minted from it. `--storage auto|hosted|s3` decides, at every startup, whether a process uses S3 or the hosted API and with which credential. The site side (the `/cli/v1/*` routes and the approval page) lives in [baalimago/slivingdoc-cloud](https://github.com/baalimago/slivingdoc-cloud) (`architecture/cli-login.md` there). This doc answers "how does a login become a key on disk, how does a key become a space token, and which store and credential does a process pick?"

Read this when: changing `login`, `logout` or `space`, the site client or its wire contract, the credentials file or its lock, the minted token source, `--storage` or the rules that pick S3 or hosted mode, the hosts a key or token may reach, the browser opener, the confirmation prompt, or the login scenarios. The [Threat model](#threat-model) lists what each rule defends against.

## Behavior

**Wire contract (v2).** The site routes take and answer JSON, set no cookies, and answer errors as `{"error", "message"}`. `start` and `token` require `Content-Type: application/json` and a body under 4 KiB; the client sends both (`call` refuses to send a larger body, `requestLimit`). `start` takes `access` (`write` or `read`) and `client` (the host name, cut by `label` to 64 printable ASCII bytes), and no space: the login is to the account. It answers `deviceCode`, `userCode`, `verificationUri`, `verificationUriComplete` (`<site>/cli/login#<userCode>`: the code travels in the fragment, so it never reaches a server log or a `Referer`), `interval` (optional) and `expiresIn`; a `503 busy` or any other error answer ends the login with the site's message. `token` answers the account CLI `key`, `access`, `expiresAt`, `endpoint` (the hosted API that belongs to this site, so a dev site's login talks to the dev API) and `account` (who approved the code). `GET /cli/v1/spaces` (Bearer key) answers `{"spaces": [{name, owner, access}]}`, the access capped by the key; `Client.Spaces` reads up to 256 KiB (`spacesLimit`) and refuses (`ErrProtocol`) a missing list, an invalid or repeated name, an unusable owner or an unknown access. An empty `owner` is a space a team owns (the site has no owner email for it): `usableOwner` accepts it in `Spaces` and `Mint` alike, and `describeSpace` shows it as `owned by a team`. `POST /cli/v1/space-token` (Bearer key) takes `space` and an optional `access` and answers `token`, `space`, `access`, `expiresAt`, `endpoint` and `owner`, or 401 `invalid_token`, 404 `no_space`, 403 `access_denied` or `space_suspended`, 429 `busy` (each a `*Refusal`). `revoke` authenticates with the credential itself: a key revokes itself and every token minted from it, a minted token only itself. It answers 204, or 401 `invalid_token` for a credential the site does not know, which counts as revoked; any other 401 is a failure.

**What the client trusts.** `sitelogin.New` accepts an https origin, or http to a loopback host (`httpstore.IsLoopback`), without a path, user information, query or fragment; `--site` passes through `normalizeEndpoint` first, and `parseSite` gives the host one spelling (`canonicalHost`: lower case, no trailing dot, no default port), so `https://WWW.slivingdoc.dev.:443/` is `DefaultSite` and gets its endpoint rule. The default site is the `www` host because the bare domain answers a `POST` with a 301. The client never follows a redirect (a 3xx is a `Refusal`), reads at most 16 KiB of an answer (`bodyLimit`; a larger success answer is `ErrProtocol`), and sanitizes the site's `error` and `message` with `httpstore.Sanitize`. `Start` requires a printable device code and a user code of exactly two groups of four consonants (`userCodePattern`), builds the approval pages itself from the site origin (`<site>/cli/login`, and `<site>/cli/login#<userCode>` for the one the browser opens), and refuses the answer unless the site's `verificationUriComplete` equals the page it built; the site's `verificationUri` is not used. So a browser only ever opens a page on the configured site, and a code shown to the person is only ever a code. An absent `interval` is 5 s, a present one at least 1 s, and `expiresIn` is capped at 1800 s, so a site cannot make the client poll hard or wait for hours. `issued` validates the key (`httpstore.ValidateToken`), the access, the endpoint (`httpstore.ValidateEndpoint`: https unless loopback), `expiresAt` (required, RFC 3339) and a printable `account` of at most 254 bytes. `Mint` validates the token, requires the space asked for, a read token when read was asked, a valid endpoint, a usable owner and an `expiresAt`. Anything else is `ErrProtocol`, and no error carries a key or token: when the credential itself is sendable, the error is a `*RejectedError` carrying it, so the caller revokes it (`Login.discard`, `mintedTokens.discard`) instead of leaving it valid and unseen.

**Polling.** `Wait` sleeps the interval before every poll, adds five seconds after each `slow_down`, and stops with `ErrCodeExpired` once the clock reaches the approval's deadline (`expiresIn` after `Start`) without polling again. `access_denied` is `ErrDenied` and `expired_token` is `ErrCodeExpired`, each with the site's message. A poll that got no answer (`ErrUnreachable`) or a 5xx, including a 5xx whose body broke off, is retried (`transient`), the pause doubling from the interval per failure in a row up to a minute (`retryWait`) and never past the deadline; if the code expires meanwhile, `ErrCodeExpired` names the last failure. Once any poll went unanswered, a later `ErrCodeExpired` (the deadline, or `expired_token`) also carries `TokenHint`: that poll may have been the one the site issued the key to. Every other error answer (a 4xx outside the contract's codes) ends the wait as `ErrRefused`. A success answer that breaks off while it is read is `ErrBrokenAnswer` and ends the wait without polling again: the site has already claimed the code, so a retry would only answer `expired_token`. It, a success answer that is larger than 16 KiB or does not decode, a key that is not even sendable, and a context that ends while a poll is in flight all end with `TokenHint` ("a login key may have been issued; revoke it on the Tokens page"), because in each case the site may have issued a key the client never saw. A cancellation during the sleep before a poll carries no hint: no poll was sent. The sleep and clock are `Config.Sleep` and `Config.Now`; the process passes `ProcessOptions.Sleep`. `Login.Run` runs under `ProcessOptions.interruptible`: the first termination signal (from `ProcessOptions.Signals`, or SIGINT and SIGTERM from the operating system when that is nil) ends its context, so Ctrl-C during a poll exits nonzero with the hint. The signal is consumed once: a second Ctrl-C while a revocation runs on `revocationContext` (up to 10 s) is ignored, and the login exits when that revocation ends. Also when a poll went unanswered earlier, a stop during the sleep before the next poll carries the hint.

**Who approved it, and what it reaches.** Whoever enters a user code first decides it. Once the site issues a key, `Login.accept` refuses, and revokes (`Login.discard`), a write key for `--read-only`, an endpoint that does not normalize, and a key from `DefaultSite` for any endpoint but `DefaultHostedEndpoint`. The login then lists the spaces the key reaches (`Client.Spaces`); a failed listing revokes the key and stores nothing, and so does a `--space` (or `--bucket`) the key does not reach, naming the spaces it does. Before anything is stored, stderr shows `approvedBy`: `Approved by ada@x (read and write) until 2026-12-26 09:00 UTC.`, the storage endpoint, the site, and each space with its access and owner (or `Spaces: none yet`). When stdin and stderr are both terminals (`ProcessOptions.terminal`, `golang.org/x/term`), the login asks `Store this login? [y/N]` and stores it only for `y` or `yes` in any case (`Login.confirm`); any other answer, an empty one, a read error or an interrupt at the prompt (the read runs beside the context, and a cancelled context is a no) revokes the key and exits nonzero. Every revocation after the key was issued (`Login.discard`, and the replaced key in `Login.report`) runs on `revocationContext`: the login's values without its cancellation, bounded by `revocationTimeout` (10 s), so an interrupt never skips it. Without a terminal nobody is asked, and `--force` stands in for the answer in the account check below; a first login, or one for a (site, endpoint) nobody else's login holds, is stored without `--force` (see Residual risks).

**The result line.** `Logged in as ada@x (read and write) until 2026-12-26 09:00 UTC; default space "notes"` (`loggedIn`, `Access.Describe`, `Expiry.Describe`); the endpoint follows the account (`at <endpoint>`) when it is not `DefaultHostedEndpoint`, and the default space only when there is one. The line always names a date, because `issued` refuses an answer without `expiresAt`; only a stored entry without `expiresAt` has no expiry, and `Login.Usable` never refuses it. The prompt (the site warning, code, pages, the warning, a browser failure, the wait, the approval, the question, the default-space, replaced-file and replaced-key notes) goes to stderr; only the result line goes to stdout. When the host name is unknown, stderr says so and the key is labelled without it (`CLI login`).

**The default space.** One default space is stored per endpoint. After a login it is `chooseDefault`: `--space` (or `--bucket`) when given, which the key must reach; else the only space listed; else the prior default of that endpoint when the key still reaches it; else none. `Login.report` says which: `The default space is "notes"; 'slivingdoc space <name>' changes it.`, `The default space changed from "a" to "b".`, or, with none, that a prior default was cleared and `Run 'slivingdoc space <name>' to choose the default space, or pass --space to serve, pull and commit.` (for no space at all: create one on the site first). `slivingdoc space` lists the key's spaces on stdout, one per line, marking the default with `*`, and says on stderr when there is no space, no default, or a default the key no longer reaches. `slivingdoc space <name>` sets the default only for a name in that list, under the lock, and only while the stored key is still the one it listed with (`Space.store`; otherwise `run the command again`). Both choose the login like a process does (`pickLogin`: `--endpoint` or `SLIVINGDOC_ENDPOINT`, else the only one), refuse an expired login before contacting the site, and a 401 from the site says to log in again.

**The browser.** `ProcessOptions.OpenBrowser` opens the page when set; otherwise `platformBrowser` starts `/usr/bin/open` on macOS, `%SystemRoot%\System32\rundll32.exe url.dll,FileProtocolHandler` on Windows (the variable looked up without regard to case, `lookupFold`, and refused unless it is an absolute path, so no `rundll32.exe` from the working directory ever runs), and `xdg-open` from `PATH` elsewhere (`findOnPath`), through `os.StartProcess` with null streams, and does not wait. A failure prints `Could not open a browser (...); open the page yourself.` and the login goes on; `--no-browser` never tries.

**The credentials file.** `credentials.Locate` reads `SLIVINGDOC_CONFIG_DIR` (absolute) from the injected environment, else mirrors `os.UserConfigDir` over it (`XDG_CONFIG_HOME` or `HOME/.config`, `HOME/Library/Application Support`, `AppData`) plus `slivingdoc`; no directory is `ErrNoConfigDir`. The file is `credentials.json`:

```json
{
  "version": 2,
  "logins": [
    { "site": "https://www.slivingdoc.dev", "endpoint": "https://api.slivingdoc.dev",
      "key": "sld_...", "access": "write", "expiresAt": "2026-12-26T09:00:00Z",
      "account": "ada@example.com" }
  ],
  "defaultSpaces": [
    { "endpoint": "https://api.slivingdoc.dev", "space": "notes" }
  ]
}
```

It holds no minted token, ever. It is read, up to 1 MiB (a larger file is `ErrMalformed`), with `strictjson`: unknown or duplicate fields, `null`, a missing or non-numeric version, an invalid endpoint, site, key, access or space, an endpoint or site with user information, a query or a fragment (`plainURL`: `login` never stores one, since `normalizeEndpoint` refuses them, so such a file was edited by hand; the refusal names the field, never the value), a malformed `expiresAt`, an empty `account`, two logins for one (site, endpoint), two default spaces for one endpoint, and a default space for an endpoint with no login are `ErrMalformed`, and no message echoes a key. `defaultSpaces` and `expiresAt` may be absent. A file whose `version` is anything but `FormatVersion` (2) is `ErrUnsupportedVersion` (a `versionError`, "it is version <n>, and this slivingdoc reads version 2 only"), read no further, so none of its fields is parsed or echoed. `versionError.withFix` adds the fix for its direction: an older version, "remove <path> and run 'slivingdoc login'"; a newer one, "a newer slivingdoc wrote it (<path>); update slivingdoc, and keep the file", since that file holds live keys that removing it would orphan without revoking them. Every command that reads it (`login`, `logout`, `space`, and `serve`, `pull` and `commit` outside `--storage s3` and without `SLIVINGDOC_TOKEN`; `version` and `-h` never read it) refuses it, `login` included: nothing rewrites a file this build cannot read. A missing file is an empty `Set`. Like ssh, `File.Load` refuses (`ErrExposed`) a credentials file that is a symbolic link (`Lstat`, then an `open` with `O_NOFOLLOW` where the platform has it, so a link swapped in between fails too) or anything but a regular file (checked through the open descriptor, which `O_NONBLOCK` keeps a planted FIFO from blocking); and on every platform but Windows a file another user owns or that group or other can read or write (`checkFile`, `chmod 600`), and a directory that is not a directory, another user owns, or that group or other can write (`CheckDir`, `chmod go-w`). The owner is compared with the effective user (`File.uid`, from `os.Geteuid` in `Locate`). A missing file is never refused, so an S3 process beside a group-writable config directory (a `0002` umask) starts. `PrepareLogin` also calls `File.CheckDir`, so a login into a directory another user owns or can write is refused before the site is contacted, file or not, and `File.Lock` and `File.Save` check again after creating the directory. `logout` and `space` need no separate check: with no file there is nothing to use, and an existing file brings its directory into `Load`'s check. Ancestors of the directory are not checked. `File.Save` creates the directory `0700`, writes a `0600` temporary file beside the target, syncs it and renames it over the target, so a reader never sees half a file.

**The lock.** `login`, `logout` and `space <name>` change the file only under `File.Lock`: an exclusive `flock` (`github.com/gofrs/flock`) on `credentials.lock` beside the file, `0600`, taken after the site answered and released before the revocation of a replaced key. It waits while another holder has it, until the context ends. `serve`, `pull`, `commit` and `space` without a name only read the file and take no lock; the rename keeps each read whole. The endpoint is stored normalized (`normalizeEndpoint`), which is what a process compares against, and `site` records where the key is sent.

**One login per endpoint.** `Login.store` refuses a login for an endpoint whose stored login another site issued (`log out of that login first (slivingdoc logout --site <site>)`, whatever the flags), so each endpoint has at most one login and one default space. `Set.Put` replaces the login of the same (site, endpoint); `Login.store` refuses to replace one another account approved unless the person confirmed at the prompt or passed `--force`. After the new login is stored, `Login.report` revokes the replaced key at its site, best effort, only when the same account approved both; a key another account approved is left valid, with a stderr note to revoke it on the Tokens page, so one person's login never withdraws another person's key. The file is read under the lock right before it is written, so a login for another endpoint that finished in another terminal meanwhile keeps its entry. Once `File.Save` succeeded the new key is stored: a failure to release the lock afterwards never revokes it. `Login.store` records the unlock error instead, `Login.report` still runs, and `Login.Run` prints the result line and then fails with `login: the login was stored, but releasing the credentials lock failed: ...; it is released when this command exits`. The lock is an `flock`, which the kernel releases when the process exits, so the next command does not wait on it, and the lock file is never to be removed.

**Logout.** `PrepareLogout` takes every stored login, narrowed to those issued by `--site` or `SLIVINGDOC_SITE` when either is set; none stored is `ErrNoLogin`, and none left after that narrowing is `ErrNoLogin` naming the site filter. `Logout.Run` revokes each key at its own `site`, which revokes every token minted from it too; a revoked key (204) or one the site no longer knows (401 `invalid_token`) is removed under the lock (`Logout.remove`), together with its endpoint's default space (`Set.Remove`), with one stdout line per removed login. `Logout.remove` deletes an entry only while its stored key is still the one just revoked: a login another process stored for the same (site, endpoint) after `PrepareLogout` read the file is kept, and stdout says `Revoked the login key of X at E; a newer login for it was kept`, so a logout never orphans a live key. A failed revocation keeps that login stored, prints no line for it, and ends the command nonzero, so the logout can be repeated.

**Minted tokens.** A process that uses a stored login never sends its key to storage. `buildService` builds `mintedTokens` for the login and the space, and mints the first token within the startup check's deadline (`probeTimeout`); a failure is a startup refusal (`mintRefusal`, `app: the stored login could not mint a token for space "x" at <site>: ...;` then the fix: `slivingdoc space` and `slivingdoc space <name>` when the space was the stored default, else check the setting it came from, list the spaces, or log in again; `try again later` for a busy or unreachable site). Each mint is `POST <login site>/cli/v1/space-token` with the key as bearer. A read login asks for `read`; a write login leaves `access` out, so the token carries the most the grant allows and a space shared read-only with a write login stays readable. The answer must name the space asked for and a read token when read was asked (`Mint`), an endpoint that normalizes to the login's own (else the token is revoked and the mint is `ErrIncompatible`), and an expiry after the moment the mint was asked (else revoked, `check the system clock`). `mintedTokens.Token` returns the held token until 80 % of its lifetime has passed (`renewalNumerator`/`renewalDenominator`), then mints another. Renewal compares wall-clock times (`wallNow` strips the monotonic reading, and the stored `renewAt` carries none), so a laptop that slept past the renewal time re-mints on waking rather than after the lifetime has passed in awake time. One mint runs at a time: the `minting` channel admits it, the mutex guards only the held token and its renewal time and is never held across the network call, and a caller waiting for another's mint gives up when its own context ends (`wait for a token: ...`, `ErrTransport`), then re-checks the token the mint left before minting itself. The httpstore adapter asks the source for every request's token (`Store.request`); a 401 from the gateway calls `Rejected`, which forgets that token if it is still current, and `Store.send` resends a replayable request (no body, `http.NoBody`, or a `GetBody`) once when the source now gives a different token. A streamed upload is not resent. Because `mintedTokens` is a `RenewingSource`, `Store.send` ends it with a `storage.Refusal` of `storage.ErrCredentialRenewed` instead of the 401's `ErrAccessDenied`, keeping the gateway's sanitized message: the pack upload fails retryable (`PACK_UPLOAD`) with a hint that the stored login's token may have expired or been renewed during the upload and to retry, followed by the storage's own line ([errors.md](./errors.md)), not with advice about `SLIVINGDOC_TOKEN`, and the next attempt mints. The same 401 also stands for a revoked token: a revoked minted token alone is forgotten (`Rejected`) and replaced by the retry's mint, so the retry succeeds; only a refusal the mint meets too (a revoked login key, a suspended account, a space no longer granted) fails the retry, with the mint's reason, typically `ACCESS_DENIED`. A `SLIVINGDOC_TOKEN` source is not renewing, so its streamed 401 stays `ErrAccessDenied`. A failed mint during a run maps to the storage taxonomy (`mintError`): a 401 from the site (the key was revoked or expired), `no_space`, `space_suspended` and any other 403 are `ErrAccessDenied`; 429 is `ErrRateLimited`; another 4xx and an answer outside the contract are `ErrIncompatible`; the rest is `ErrTransport`. Minted tokens live only in the process's memory: never in the file, never in a log. The login path does not call `GET /v1/token`: the mint answer names the space, and the startup access check proves the token.

**Which storage a process uses.** `resolveStorage` runs first in `Flags.resolve`, for `serve`, `pull` and `commit` alike. In `auto` it collects the S3 signals (`s3Signals`), which decide whether a stored login applies: any of `awsSignals` that is set (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_REGION`, `AWS_DEFAULT_REGION`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_ROLE_ARN`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_S3`, `SLIVINGDOC_PATH_STYLE`), any `AWS_CONTAINER_CREDENTIALS_*` variable, the S3-only flags `--region` and `--path-style`, and an existing `~/.aws/credentials` or `~/.aws/config` (under `HOME`, or `USERPROFILE` on Windows). The login is `pickLogin`'s: the one for `--endpoint` or `SLIVINGDOC_ENDPOINT` when either is set (`Set.ForEndpoint`), else the only one stored (`Set.Only`). The precedence, exactly:

| `--storage` | `SLIVINGDOC_TOKEN` | Stored login | Space | S3 signals | Result |
|---|---|---|---|---|---|
| `s3` | ignored | ignored (file never read) | explicit | used | S3 |
| `hosted` | set | any (never read) | any; none: the token's own space from `GET /v1/token`, or, on a server without it, a refusal asking for `--space` | ignored | hosted with the variable's token |
| `hosted` | unset | usable | explicit, else the stored default; neither → refusal naming `slivingdoc space <name>` | ignored | hosted with tokens minted from the login, at its endpoint |
| `hosted` | unset | none, or none for this endpoint | any | ignored | refusal: run `slivingdoc login` |
| `auto` | set | any | any | `--endpoint` flag, `AWS_ENDPOINT_URL` or `AWS_ENDPOINT_URL_S3` | refusal naming them: pass `--storage hosted` or `--storage s3` |
| `auto` | set | any (as for `hosted`) | as for `hosted` | none of those three (any other signal is ignored) | hosted with the variable's token |
| `auto` | unset | usable | the stored default | any | hosted with minted tokens |
| `auto` | unset | usable | explicit (`--space`, `--bucket`, `SLIVINGDOC_SPACE` or `SLIVINGDOC_BUCKET`) | any | refusal naming them: pass `--storage hosted` or `--storage s3` |
| `auto` | unset | usable | explicit | none | hosted with minted tokens |
| `auto` | unset | usable | none and no stored default | any | refusal naming `slivingdoc space <name>`, `--space`, or `--storage s3 --bucket` |
| `auto` | unset | none, or none for this endpoint | any | any | S3 |
| `auto` or `hosted` | unset | several (one per endpoint), no explicit endpoint | any | any | refusal: pass `--endpoint` |

So the common case stays one command: after `slivingdoc login` (and `slivingdoc space <name>` when the account has several spaces), `slivingdoc serve` with no space uses the login and its default space, whatever AWS configuration the machine has, because S3 has no bucket to use. A command line that names its space gets the login only when nothing on the machine configures S3; otherwise it must say which store it means. An expired login that would be used is a refusal (`Login.Usable`) naming the date, `run 'slivingdoc login' again` and `--storage s3`; nothing is sent. The variable's token keeps the endpoint rule (`--endpoint`, `SLIVINGDOC_ENDPOINT`, `DefaultHostedEndpoint`); it never borrows a login's endpoint. The variable's token is refused in `auto` only beside a setting that points S3 at a host (`tokenDestinations`: the `--endpoint` flag and `destinationSignals`, `AWS_ENDPOINT_URL` and `AWS_ENDPOINT_URL_S3`). This is an intent check, not a leak guard: hosted mode never reads the two variables, so the token cannot follow them, but an S3 host configured on purpose beside a token is a guess `auto` will not make; `--storage hosted` sends the token only to the hosted endpoint. A region, AWS credentials, a profile or the `~/.aws` files are no refusal (a profile may carry an `endpoint_url`, but hosted mode reads none of them), so `SLIVINGDOC_TOKEN` with `serve --space` works on a machine that also uses AWS. `SLIVINGDOC_ENDPOINT` names the hosted API and is no refusal. At startup `logStorage` records the outcome at Info: `storage selected backend=s3|hosted endpoint=<url or aws-default> space=<bucket, or "the token's own" before the lookup> token=none|env|login`, never a key or token; an S3 process with no endpoint of its own (an explicitly empty `--endpoint` included) logs the variable the SDK will read, `AWS_ENDPOINT_URL_S3` before `AWS_ENDPOINT_URL`, as `<scheme>://<host> (<name>)` (`endpointForLog`: scheme, host and port only, with no user information, path or IPv6 zone; a value without a scheme or a host is `an unparsable URL`), and otherwise `aws-default (SDK: env or profile)`, because a shared profile's `endpoint_url` may still redirect the SDK.

**`--space` and `--bucket`.** `--space` and `SLIVINGDOC_SPACE` are the hosted names of `--bucket` and `SLIVINGDOC_BUCKET`: one setting, on `serve`, `pull`, `commit` and `login` (the variables on the first three; on `login` it sets the default space). `flagSpace` resolves the two flags and `resolveBucket` adds the two variables: a flag beats the variables, an explicitly empty flag does not fall back to them, and both spellings of one layer with different values are a refusal naming both (`--bucket "a" and --space "b" name different spaces; they are one setting, so pass one of them`, `SLIVINGDOC_BUCKET "a" and SLIVINGDOC_SPACE "b" name different spaces; ...`); the same value twice is fine. `config.bucketFrom` records the spelling used, so each refusal and the `hosted space resolved` record name it; hosted hints that name no source say `--space`, and the S3 `bucket is required` refusal names both.

**The space a `SLIVINGDOC_TOKEN` process uses.** A variable's token asks the API which space it reaches before the store is built (`resolveHostedSpace` over `httpstore.DescribeToken`, [hosted-mode.md](./hosted-mode.md)), and never picks between two answers silently. With no space named it uses the token's own space, whatever login is stored; a token process never reads the credentials file, so a broken or foreign file never stops a token user, and a stored default space never applies to a token. Otherwise the named space must be the token's, and the refusal names the fix for where it came from (`spaceMismatch`): drop that flag or unset that variable, or use a token made for it. A server without `GET /v1/token` keeps a given space, which the access check then proves; with none it refuses asking for `--space`. `setup` logs the space it settled on once (`hosted space resolved`).

**The key reaches only its site; a token only its endpoint.** The key goes in the `Authorization` header of the site's `spaces`, `space-token` and `revoke` routes only, at the `site` stored with it; `httpstore` never sees it. A minted token goes only to the login's endpoint, which the mint answer must name. With no explicit endpoint, `Set.Only` picks the only login; several are a refusal asking for `--endpoint`, so a second login never silently redirects a command line. An explicit `--endpoint` or `SLIVINGDOC_ENDPOINT` selects exactly the login stored for it (`Set.ForEndpoint`, after `normalizeEndpoint`), so a different endpoint means the login does not apply: S3 under `auto`, a refusal naming the endpoint the stored login is for under `hosted`. `--storage s3` never reads the token or the file, and in `auto` an `--endpoint` flag, `AWS_ENDPOINT_URL` or `AWS_ENDPOINT_URL_S3` beside `SLIVINGDOC_TOKEN` is a refusal, which closes the old gotcha of an S3 `--endpoint` receiving a stray `SLIVINGDOC_TOKEN` ([hosted-mode.md](./hosted-mode.md)).

**The credentials file at startup.** Outside `s3` mode, a process without `SLIVINGDOC_TOKEN` reads the file (`loadLogins`) in `resolveStorage`; a process with it never does. No configuration directory in the environment means no logins. `loadLogins` returns the bare error for a file that exists but cannot be read (one of another version included), and `resolveStorage` refuses startup naming the file: for another version, the file's own fix followed by `, or pass --storage s3 to use S3`; otherwise `; fix or remove the file, or pass --storage s3 to use S3`. `version` and `-h` exit before `Setup`, so they never read it. A stored endpoint or site with user information, a query or a fragment is refused at load (`ErrMalformed`), so no such value leaves `File.Load`. As defense in depth, an endpoint or site read back from the file is also printed through `mcp.Redact` wherever it reaches the terminal (`Login.store`'s refusals and notes, `Logout.Run`), and the configuration refusals of `resolveStorage` are redacted by `setup`.

**Refused tokens.** When the hosted startup check refuses a minted token (`config.tokenOrigin` is `originLogin`), `hostedCheckError` says `app: hosted storage refused the token minted for space "x": ...; run 'slivingdoc space' to list the login's spaces, or 'slivingdoc login' again` instead of naming `SLIVINGDOC_TOKEN`. A variable's token refused for the stored default space says `check SLIVINGDOC_TOKEN, or pass --space: the space "x" is the stored default space`. A refusal while `serve` runs, after the one resend with a new token, is still reported by the notebook's fixed `ACCESS_DENIED` message, which names `SLIVINGDOC_TOKEN`: the notebook does not know where its token came from ([errors.md](./errors.md)).

## Threat model

**Assets.** The account CLI key (it lists the account's spaces and mints tokens for any of them, read and write or read only, for 90 days); a minted space token (bearer access to one space for at most an hour); the user code and device code of an open approval; the credentials file and its default spaces; the notebook content a token can read or overwrite; and the choice of store, which decides where a process sends notes and credentials.

**Actors.** The person running `login` (trusted, but can be rushed or phished); another person who sees or is sent the user code or the approval page; another local user on the same machine; a malicious or compromised site, or a site reached through a mistaken `--site` or `SLIVINGDOC_SITE`; a malicious or compromised storage endpoint; a network attacker (confined by TLS to what a site or endpoint answers); and an operator whose machine carries both AWS configuration and a stored login.

**Trust boundaries.** The site's answers (start, token, spaces, space-token, revoke) are untrusted input until validated. The browser is outside the process: the client only opens a page it built. The credentials file and its directory are trusted only when the effective user owns them and nobody else can write them. The environment and flags are the operator's, but a stray variable is not proof of intent. The site that issued a key is the only host that receives it; the storage endpoint receives only minted tokens, and only the endpoint the login was issued for.

| Threat | Mitigation |
|---|---|
| Someone else approves the code first (a phished or shoulder-surfed code), so the victim stores the attacker's key, or replaces their own login with it | `approvedBy` shows the approver, access, expiry, endpoint, site and every space with its owner before anything is stored (a team-owned space shows `owned by a team`, no identity, so for it the `Approved by` line is the only signal of whose login this is); a terminal asks `Store this login? [y/N]` and revokes on anything but yes, an interrupt included; without a terminal a login over another account's entry is refused and revoked unless `--force`; the result line names the approver and the default space |
| The attacker's account reaches a space the victim then writes notes into | the spaces and their owners are shown before storing (a team-owned space names no owner, only `a team`, so the approver line is what identifies it); `--space` must be among them; the default space is set only from that list (`chooseDefault`, `Space.store`), and `space` prints the owner of each |
| A login replaces and revokes another person's valid key | `Login.report` revokes a replaced key only when the same account approved both; otherwise it prints a note |
| A mistaken or hostile `--site` / `SLIVINGDOC_SITE` issues a key for its own endpoint, then replaces or revokes a real login | stderr names a non-default site and its source before `start`; `DefaultSite` must issue for `DefaultHostedEndpoint`; a login from one site never replaces or revokes a login another site issued for the endpoint (`log out of that login first`); the result line names a non-default endpoint |
| The storage endpoint (or anything the store talks to) captures the account key | the key is sent only to its site's `/cli/v1/*` routes; `httpstore` is given a `TokenSource` of minted tokens and never the key; a minted token reaches one space for at most an hour |
| A site mints a token for another space, with more access than asked, or for another endpoint | `Mint` refuses another space and write for read; `mintedTokens.mint` refuses an endpoint other than the login's; each such token is revoked |
| A captured minted token is replayed | it expires within an hour; `logout` (or revoking the key on the Tokens page) revokes every minted token with the key |
| Minted tokens pile up on disk | they are never written: held in memory only, re-minted per process |
| The site answers a page on another host, a `file:` URL, or a code carrying terminal escapes | the client builds both pages from the site origin, puts the code in the fragment, requires `verificationUriComplete` to match, and requires the consonant code shape |
| The site answers a write key for `--read-only` | `Login.accept` refuses and revokes; a read login mints only read tokens, and `Mint` refuses a write answer |
| A site makes the client poll hard, wait for hours, or read unbounded answers | interval default 5 s and floor 1 s, `expiresIn` capped at 1800 s, answers read up to 16 KiB (the space list 256 KiB), requests under 4 KiB |
| A key or token is issued but lost (broken, oversize or undecodable answer, cancellation mid-poll, an unanswered poll before the code expired, a refused answer, a failed space listing, an interrupt at the prompt) | a sendable credential is revoked (`Login.discard`, `mintedTokens.discard`, on `revocationContext` so an interrupt does not skip it); otherwise the error carries `TokenHint` |
| `logout` believes a key is revoked when it is not, or removes a newer login | only 204 or 401 `invalid_token` count as revoked; anything else keeps the entry and exits nonzero; an entry whose key changed since the logout read it is kept |
| Another local user reads the key or plants their own login | ownership and mode checks on the file and directory, `O_NOFOLLOW` and a symbolic link refusal, regular files only, 1 MiB bound, `0600`/`0700` on write |
| A login overwrites a credentials file this build cannot read (another version, possibly a newer build's), losing the keys it holds | `File.Load` refuses any version but 2 with `ErrUnsupportedVersion` in every command that reads the file, `login` included; an older file is removed by the person, and a newer build's file is kept, with the advice to update slivingdoc instead, so its keys are never orphaned |
| A `SLIVINGDOC_TOKEN` process picks up a stored login's default space, sending a space token's requests to a space the operator did not name | a token process never reads the credentials file: its space is the token's own (`GET /v1/token`) or the one given |
| Two logins, a login and a logout, or `space` and a login interleave and lose an entry | `File.Lock` around load, change and save; `space <name>` stores only while the key it listed with is still stored |
| A stored login silently turns an S3 command line hosted, sending notes to the wrong store | in `auto` an explicit space plus any S3 signal is a refusal; only the stored default space, or `--storage hosted`, picks the login over S3 configuration; `logStorage` records the outcome |
| A stray `SLIVINGDOC_TOKEN` goes to a host the operator meant for S3 | hosted mode reads only `--endpoint`, `SLIVINGDOC_ENDPOINT` or the default, never the AWS endpoint variables; in `auto` the token beside the `--endpoint` flag, `AWS_ENDPOINT_URL` or `AWS_ENDPOINT_URL_S3` is a refusal (an intent check), and `--storage hosted` states the intent |
| Logins at two endpoints resolve to the wrong one | `Set.Only` refuses as ambiguous; only `--endpoint` or `SLIVINGDOC_ENDPOINT` chooses |

**Residual risks.**

- A person at a terminal who answers `y` without reading the approval, or a script that passes `--force`, accepts another account's approval.
- Without a terminal nobody confirms the approver: a first login, or one for a (site, endpoint) no other account's login holds, is stored on the approval alone, and when the approver's account has one space it becomes the default. Requiring `--force` for every such login was considered and not done: an agent or script running `login` would pass it every time, which adds a step but no check. `approvedBy` on stderr and the result line naming the approver and the default space are what a script can check.
- The key reaches every space the account can reach, for 90 days, so the credentials file is worth more than any one space token. Its protection is the file's mode and ownership checks, the key never leaving for storage, and revocation on the Tokens page or by `logout`.
- On Windows the credentials file has no owner or mode check and no `O_NOFOLLOW`: it relies on the ACLs of the user profile (`AppData`) that `Locate` places it in, and on `Load`'s `Lstat` check against a symbolic link, which a swap between the check and the open could defeat. An owner-only DACL was not implemented: it needs the Windows security API and a Windows host to test it, neither of which the gate has.
- Ancestors of the configuration directory are not checked; a directory another user can write above it could replace it.
- An S3 setup that uses none of the listed signals (an EC2 instance role through instance metadata, with the default region) is invisible to `s3Signals`: an explicit space with a stored login goes hosted. The Info record and `--storage s3` are the remedies.
- A process reads the file without the lock, so it can read the file an instant before a concurrent login replaces it; it then uses the older key, which stays valid unless the same account's login revoked it.
- The site itself is trusted to issue keys and tokens only for the approving account's grants and to report `account` and `owner` truthfully; a compromised default site can still mint tokens for the default endpoint.
- The user code is shown on stderr and in the browser's address bar fragment; anyone who reads it within its lifetime can approve it first, which the confirmation above mitigates but cannot prevent.
- A streamed upload refused with 401 is not resent. Under a stored login it fails that one operation with a retryable `PACK_UPLOAD` error whose hint says the token may have expired or been renewed and to retry, with the storage's own message; the next attempt mints a new token, which also replaces a minted token revoked alone; only a refusal the mint meets too (a revoked login key, a suspended account) fails that attempt, with the mint's reason. Under `SLIVINGDOC_TOKEN` it is `ACCESS_DENIED`, as before.

## Gotchas

- The key and the default space are read once at startup; after a new login or `space <name>`, an MCP host must restart `serve`. Minted tokens renew within the run.
- A space renamed or left on the site is no longer in the key's list: the first mint answers `no_space`, and the startup refusal says to run `slivingdoc space`.
- The file is read through the injected environment (`ProcessOptions.Env`), never `os.UserConfigDir`, so tests stay hermetic: `internal/integrationtest` drops `SLIVINGDOC_CONFIG_DIR`, `SLIVINGDOC_STORAGE`, `SLIVINGDOC_SITE`, `SLIVINGDOC_TOKEN` and `SLIVINGDOC_ENDPOINT` (`sanitizedEnv`) and gives every helper its own empty `SLIVINGDOC_CONFIG_DIR`; the `internal/app` process helper drops the same names and every name it sets itself (`helperEnv`) before appending its own values, so the child sees each name once; `release_test.go` drops them and points every binary at a per-run empty directory made in `TestMain`; and `testProcess` passes no `HOME`.
- Tests that write a credentials file create its directory `0700` themselves (a `cfg` subdirectory of `t.TempDir()`): under a `0002` umask a bare `t.TempDir()` is group-writable, which `ErrExposed` refuses.
- `os/exec` is banned module-wide (`TestNoGitExecutableOrGit2goImport`), so the browser opener finds and starts its program with `os.StartProcess`.
- The integration helper takes the operating system's signals only when `SLIVINGDOC_INTEGRATION_OS_SIGNALS` is set (`helperSignalsEnv`), for the interrupt scenario; and `SLIVINGDOC_INTEGRATION_SITE_ROUTE` (`helperSiteRouteEnv`) sends every site request to a reference site through `ProcessOptions.SiteClient` (`routedSite`), so the default site's endpoint rule runs black box against `sitetest.SetOrigin(DefaultSite)`.
- The integration helper's `Sleep` waits a hundredth of what the site asks for; exact poll timing is pinned by the `sitelogin` unit tests over a fake clock, not by the scenarios. Renewal timing is pinned by `internal/app` unit tests over a fake clock; the lifecycle scenario only shows a second mint with a short `SetMintLifetime`.
- `sitetest` emits `expiresAt` with sub-second precision: truncated to seconds, a short lifetime can land before the moment the mint was asked, which `mintedTokens.mint` refuses.
- Scenario helpers run on pipes, so they are never on a terminal: the prompt is covered by `internal/app` unit tests through `ProcessOptions.Terminal` and `Stdin`. Each helper also gets an empty `HOME` (`spawnHelperIn`), because a developer's `~/.aws` files are an S3 signal.
- `Set.Put` returns `ErrNoLogin` when nothing was replaced: absence is an error by the code style. It never sets a default space; `Set.SetDefaultSpace` does, and `Set.Remove` drops the endpoint's default with its last login.
- CI keeps using `SLIVINGDOC_TOKEN`; the login is for people.
