# Login, stored credentials, and storage selection

`slivingdoc login` gets a hosted API token through a browser approval (the device flow, like `gh auth login`) and stores it, so `serve`, `pull` and `commit` reach a hosted space without `SLIVINGDOC_TOKEN`. `slivingdoc logout` revokes it. `--storage auto|hosted|s3` decides, at every startup, whether a process uses S3 or the hosted API and with which token. The site side (the `/cli/v1/*` routes and the approval page) lives in [baalimago/slivingdoc-cloud](https://github.com/baalimago/slivingdoc-cloud) (`architecture/cli-login.md` there). This doc answers "how does a login become a token on disk, and which store and token does a process pick?"

Read this when: changing `login` or `logout`, the site client or its wire contract, the credentials file or its lock, `--storage` or the rules that pick S3 or hosted mode, the endpoint a stored token may reach, the browser opener, the confirmation prompt, or the login scenarios. The [Threat model](#threat-model) lists what each rule defends against.

## Flow

```text
slivingdoc login [--bucket s] [--read-only] [--site url] [--no-browser] [--default] [--force]
  Setup: PrepareLogin
    credentialsFile(env) → credentials.Locate(SLIVINGDOC_CONFIG_DIR | <user config dir>/slivingdoc)
    File.Load (refuse a malformed or exposed file now), File.CheckDir, httpstore.ValidateSpace(--bucket)
    siteClient(--site | SLIVINGDOC_SITE | https://www.slivingdoc.dev)   https unless loopback, origin only
  Run: Login.Run
    site not the default → stderr: Logging in through <site> (from --site | SLIVINGDOC_SITE).
    POST <site>/cli/v1/start {space, access, client: hostname}  (application/json, < 4 KiB)
      → Approval: userCode must match ^[BCDFGHJKLMNPQRSTVWXZ]{4}-[BCDFGHJKLMNPQRSTVWXZ]{4}$;
        pages built locally: <site>/cli/login and <site>/cli/login#<userCode>;
        the site's verificationUriComplete must equal the second; interval absent → 5 s; expiresIn ≤ 1800 s
    stderr: code + complete page + plain page + "only approve if you started this";
      openBrowser(complete page) unless --no-browser (failure: a hint)
    Client.Wait: sleep(interval) → POST /cli/v1/token {deviceCode}
        authorization_pending → again; slow_down → interval += 5 s; access_denied → ErrDenied;
        expired_token or the deadline passed → ErrCodeExpired (+ TokenHint once any poll went unanswered)
        no answer (ErrUnreachable) or a 5xx, whole or broken off → retry, the pause doubling up to a minute, capped at the deadline
        a 200 that breaks off, exceeds 16 KiB, or does not decode, an unsendable token,
          or ctx ending while a poll is in flight → error + TokenHint ("a token may have been issued; revoke it on the Tokens page")
        any other error answer → ErrRefused
        200 → Issued (token, space, access, expiresAt, endpoint, account, owner), validated;
              a sendable token in an answer outside the contract → *RejectedTokenError → discard (revoke)
    stderr: Approved by <account> for space "<space>" (<access>), owned by <owner>. / Storage endpoint / Site
    Login.accept, each refusal → discard (revoke):
      a write token for --read-only; another space than --bucket; an endpoint that does not normalize;
      the default site with an endpoint other than https://api.slivingdoc.dev
    stdin and stderr on a terminal → "Store this login? [y/N]"; anything but y/yes, or an interrupt → discard
    (every discard and report revocation runs on revocationContext: not cancelled by an interrupt, 10 s)
    Login.store, under File.Lock (credentials.lock beside the file):
      File.Load
      the same (endpoint, space) stored from another site → refusal "log out of that login first" → discard
      the same (endpoint, space) approved by another account, not confirmed and no --force → refusal → discard
      --default over a default another account approved, not confirmed and no --force → refusal → discard
      Set.Put; Set.SetDefault only when no default is stored, for --default, or for a re-login of the default
      File.Save (0600 temp file + rename, dir 0700); a Load or Save failure → discard
    Login.report (stderr):
      "The default login changed from X to Y." or "The default login stays X; use --default to switch."
      replaced a different token: same account → revoke it at its site (best effort);
        another or unknown account → keep it, and say to revoke it on the Tokens page
    stdout: Logged in as <account> to space "<space>"[ at <endpoint>] (<access>) until <date>[, owned by <owner>]

slivingdoc logout [--bucket s] [--site url]
  Setup: PrepareLogout: logins of --bucket (else the default's space), narrowed to --site | SLIVINGDOC_SITE
  Run: for each: POST <its site>/cli/v1/revoke (Bearer token); 204 or 401 invalid_token → remove; else keep, report
       Logout.remove under File.Lock: File.Load → Set.Remove only where the stored token is still the revoked one → File.Save
       stdout, per removed login: Logged out of space "<space>" at <endpoint>; the token was revoked
       per login replaced meanwhile: Revoked the token for space "<space>" at <endpoint>; a newer login for it was kept

serve | pull | commit: Flags.resolve → resolveStorage(flags, env, {GOOS, now, stat})
  mode = --storage | SLIVINGDOC_STORAGE | auto
  s3     → bucket from --bucket | SLIVINGDOC_BUCKET only; token and logins never read
  signals (auto only) = s3Signals: awsSignals variables, AWS_CONTAINER_CREDENTIALS_*, --region, --path-style,
                        ~/.aws/credentials, ~/.aws/config
  bucket = --bucket (bucketFromFlag) | SLIVINGDOC_BUCKET (bucketFromEnv) | none
  SLIVINGDOC_TOKEN set → auto and (--endpoint flag, AWS_ENDPOINT_URL or AWS_ENDPOINT_URL_S3) → refusal (an intent check:
                         an S3 host was configured on purpose); pass --storage hosted or --storage s3
                         (a region, AWS credentials and the ~/.aws files are no refusal: hosted never reads them)
                       → hosted, origin env, endpoint --endpoint | SLIVINGDOC_ENDPOINT | DefaultHostedEndpoint;
                         the bucket stays as named or empty; the credentials file is not read here
  loadLogins; no bucket → the default login's space ("defaulted", bucketFromLogin; kept only if the outcome is hosted)
  login = explicit endpoint ? Set.Lookup(endpoint, space) : Set.ForSpace(space)
    none      → auto: S3; hosted: refusal (names the endpoint the login was issued for)
    ambiguous → refusal: pass --endpoint (also when the default names one of them)
    found     → auto, bucket not defaulted, any signal → refusal
              → expired → refusal: run 'slivingdoc login --bucket <space>', or pass --storage s3
              → hosted, origin login, endpoint = the login's
  buildService (hosted) → resolveHostedSpace (httpstore.DescribeToken): no bucket → the token's space (bucketFromToken);
    a bucket the token does not reach (--bucket, SLIVINGDOC_BUCKET, or a stored login's own) → refusal (spaceMismatch)
    ErrTokenLookupUnsupported: a bucket → kept; none → defaultLoginSpace: loadLogins, the default login's space
      if issued for the same endpoint, else refusal naming why (no default, the login's endpoint, an unreadable file):
      pass the space name as --bucket or SLIVINGDOC_BUCKET
  checkStore → hostedCheckError: a refused token's hint follows tokenOrigin, then bucketFrom
  setup order: logStorage (Info "storage selected" backend=s3|hosted endpoint=…[ (AWS_ENDPOINT_URL)] space=… token=none|env|login),
    engine open, buildService, then Info "hosted space resolved" space=… from=--bucket|SLIVINGDOC_BUCKET|default login|token
```

## Behavior

**Wire contract.** The site routes take and answer JSON, set no cookies, and answer errors as `{"error", "message"}`. `start` and `token` require `Content-Type: application/json` and a body under 4 KiB; the client sends both (`post` refuses to send a larger body, `requestLimit`). `start` takes `space` (optional), `access` (`write` or `read`) and `client` (the host name, cut by `label` to 64 printable ASCII bytes) and answers `deviceCode`, `userCode`, `verificationUri`, `verificationUriComplete` (`<site>/cli/login#<userCode>`: the code travels in the fragment, so it never reaches a server log or a `Referer`), `interval` (optional) and `expiresIn`; a `503 busy` or any other error answer ends the login with the site's message. `token` answers the token, `space`, `access`, `expiresAt`, `endpoint` (the hosted API that belongs to this site, so a dev site's login talks to the dev API), `account` (who approved the code) and `owner` (who owns the space). `revoke` authenticates with the token itself and answers 204, or 401 `invalid_token` for a token the site does not know, which counts as revoked; any other 401 is a failure.

**What the client trusts.** `sitelogin.New` accepts an https origin, or http to a loopback host (`httpstore.IsLoopback`), without a path, user information, query or fragment; `--site` passes through `normalizeEndpoint` first, and `parseSite` gives the host one spelling (`canonicalHost`: lower case, no trailing dot, no default port), so `https://WWW.slivingdoc.dev.:443/` is `DefaultSite` and gets its endpoint rule. The default site is the `www` host because the bare domain answers a `POST` with a 301. The client never follows a redirect (a 3xx is a `Refusal`), reads at most 16 KiB of an answer (a larger success answer is `ErrProtocol`), and sanitizes the site's `error` and `message` with `httpstore.Sanitize`. `Start` requires a printable device code and a user code of exactly two groups of four consonants (`userCodePattern`), builds the approval pages itself from the site origin (`<site>/cli/login`, and `<site>/cli/login#<userCode>` for the one the browser opens), and refuses the answer unless the site's `verificationUriComplete` equals the page it built; the site's `verificationUri` is not used. So a browser only ever opens a page on the configured site, and a code shown to the person is only ever a code. An absent `interval` is 5 s, a present one at least 1 s, and `expiresIn` is capped at 1800 s, so a site cannot make the client poll hard or wait for hours. `issued` validates the token (`httpstore.ValidateToken`), the space (`httpstore.ValidateSpace`), the access, the endpoint (`httpstore.ValidateEndpoint`: https unless loopback), `expiresAt` (required, RFC 3339), and a printable `account` and `owner` of at most 254 bytes; anything else is `ErrProtocol`, and no error carries the token. When the token itself is sendable, the error is a `*RejectedTokenError` carrying it, so `Login.Run` revokes it (`Login.discard`) instead of leaving a minted token valid and unseen.

**Polling.** `Wait` sleeps the interval before every poll, adds five seconds after each `slow_down`, and stops with `ErrCodeExpired` once the clock reaches the approval's deadline (`expiresIn` after `Start`) without polling again. `access_denied` is `ErrDenied` and `expired_token` is `ErrCodeExpired`, each with the site's message. A poll that got no answer (`ErrUnreachable`) or a 5xx, including a 5xx whose body broke off, is retried (`transient`), the pause doubling from the interval per failure in a row up to a minute (`retryWait`) and never past the deadline; if the code expires meanwhile, `ErrCodeExpired` names the last failure. Once any poll went unanswered, a later `ErrCodeExpired` (the deadline, or `expired_token`) also carries `TokenHint`: that poll may have been the one the site issued the token to. Every other error answer (a 4xx outside the contract's codes) ends the wait as `ErrRefused`. A success answer that breaks off while it is read is `ErrBrokenAnswer` and ends the wait without polling again: the site has already claimed the code, so a retry would only answer `expired_token`. It, a success answer that is larger than 16 KiB or does not decode, a token that is not even sendable, and a context that ends while a poll is in flight all end with `TokenHint` ("a token may have been issued; revoke it on the Tokens page"), because in each case the site may have minted a token the client never saw. A cancellation during the sleep before a poll carries no hint: no poll was sent. The sleep and clock are `Config.Sleep` and `Config.Now`; the process passes `ProcessOptions.Sleep`. `Login.Run` runs under `ProcessOptions.interruptible`: the first termination signal (from `ProcessOptions.Signals`, or SIGINT and SIGTERM from the operating system when that is nil) ends its context, so Ctrl-C during a poll exits nonzero with the hint. The signal is consumed once: a second Ctrl-C while a revocation runs on `revocationContext` (up to 10 s) is ignored, and the login exits when that revocation ends. Also when a poll went unanswered earlier, a stop during the sleep before the next poll carries the hint.

**Who approved it.** Whoever enters a user code first decides it, so once the site issues a token, and before anything is stored, stderr shows it (`approvedBy`): `Approved by ada@x for space "notes" (read and write), owned by bob@y.`, then the storage endpoint and the site. `Login.accept` then refuses, and revokes (`Login.discard`), a write token for `--read-only`, a token for another space than `--bucket`, an endpoint that does not normalize, and a token from `DefaultSite` for any endpoint but `DefaultHostedEndpoint`. When stdin and stderr are both terminals (`ProcessOptions.terminal`, `golang.org/x/term`), the login asks `Store this login? [y/N]` and stores it only for `y` or `yes` in any case (`Login.confirm`); any other answer, an empty one, a read error or an interrupt at the prompt (the read runs beside the context, and a cancelled context is a no) revokes the token and exits nonzero. Every revocation after the token was issued (`Login.discard`, and the replaced token in `Login.report`) runs on `revocationContext`: the login's values without its cancellation, bounded by `revocationTimeout` (10 s), so an interrupt never skips it. Without a terminal nobody is asked, and `--force` stands in for the answer in the account checks below; a first login, or one for a space nobody else's login holds, is stored without `--force` (see Residual risks).

**The result line.** `Logged in as ada@x to space "notes" (read and write) until 2026-12-26 09:00 UTC, owned by bob@y` (`loggedIn`, `Access.Describe`, `Expiry.Describe`); the endpoint follows the space (`at <endpoint>`) when it is not `DefaultHostedEndpoint`, and the owner only when it differs from the approver. The line always names a date, because `issued` refuses an answer without `expiresAt`; only a stored entry without `expiresAt` has no expiry, and `Login.Usable` never refuses it. The prompt (the site warning, code, pages, the warning, a browser failure, the wait, the approval, the question, the default and replaced-token notes) goes to stderr; only the result line goes to stdout. When the host name is unknown, stderr says so and the token is labelled without it (`CLI login`).

**The browser.** `ProcessOptions.OpenBrowser` opens the page when set; otherwise `platformBrowser` starts `/usr/bin/open` on macOS, `%SystemRoot%\System32\rundll32.exe url.dll,FileProtocolHandler` on Windows (the variable looked up without regard to case, `lookupFold`, and refused unless it is an absolute path, so no `rundll32.exe` from the working directory ever runs), and `xdg-open` from `PATH` elsewhere (`findOnPath`), through `os.StartProcess` with null streams, and does not wait. A failure prints `Could not open a browser (...); open the page yourself.` and the login goes on; `--no-browser` never tries.

**The credentials file.** `credentials.Locate` reads `SLIVINGDOC_CONFIG_DIR` (absolute) from the injected environment, else mirrors `os.UserConfigDir` over it (`XDG_CONFIG_HOME` or `HOME/.config`, `HOME/Library/Application Support`, `AppData`) plus `slivingdoc`; no directory is `ErrNoConfigDir`. The file is `credentials.json`:

```json
{
  "version": 1,
  "default": { "endpoint": "https://api.slivingdoc.dev", "space": "notes" },
  "logins": [
    { "endpoint": "https://api.slivingdoc.dev", "space": "notes", "site": "https://www.slivingdoc.dev",
      "token": "sld_...", "access": "write", "expiresAt": "2026-12-26T09:00:00Z",
      "account": "ada@example.com", "owner": "ada@example.com" }
  ]
}
```

It is read, up to 1 MiB (a larger file is `ErrMalformed`), with `strictjson`: unknown or duplicate fields, `null`, another `version`, an invalid endpoint, site, space, token or access, a malformed `expiresAt`, an empty `account` or `owner`, two logins for one (endpoint, space), and a `default` without its login are `ErrMalformed`, and no message echoes a token. `default`, `expiresAt`, `account` and `owner` may be absent. A missing file is an empty `Set`. Like ssh, `File.Load` refuses (`ErrExposed`) a credentials file that is a symbolic link (`Lstat`, then an `open` with `O_NOFOLLOW` where the platform has it, so a link swapped in between fails too) or anything but a regular file (checked through the open descriptor, which `O_NONBLOCK` keeps a planted FIFO from blocking); and on every platform but Windows a file another user owns or that group or other can read or write (`checkFile`, `chmod 600`), and a directory that is not a directory, another user owns, or that group or other can write (`CheckDir`, `chmod go-w`). The owner is compared with the effective user (`File.uid`, from `os.Geteuid` in `Locate`). A missing file is never refused, so an S3 process beside a group-writable config directory (a `0002` umask) starts. `PrepareLogin` also calls `File.CheckDir`, so a login into a directory another user owns or can write is refused before the site is contacted, file or not, and `File.Lock` and `File.Save` check again after creating the directory. `logout` needs no separate check: with no file there is nothing to log out, and an existing file brings its directory into `Load`'s check. Ancestors of the directory are not checked. `File.Save` creates the directory `0700`, writes a `0600` temporary file beside the target, syncs it and renames it over the target, so a reader never sees half a file.

**The lock.** `login` and `logout` change the file only under `File.Lock`: an exclusive `flock` (`github.com/gofrs/flock`) on `credentials.lock` beside the file, `0600`, taken after the site answered and released before any revocation of a replaced token. It waits while another login or logout holds it, until the context ends. `serve`, `pull` and `commit` only read the file and take no lock; the rename keeps each read whole. The endpoint is stored normalized (`normalizeEndpoint`), which is what a process compares against, and `site` records where `logout` revokes the token.

**One login per (endpoint, space).** `Set.Put` replaces the login of the same key and leaves the default alone. `Login.store` refuses to replace a login another site issued (`log out of that login first`, whatever the flags), and a login another account approved unless the person confirmed at the prompt or passed `--force`. After the new login is stored, `Login.report` revokes the replaced token at its site, best effort, only when the same account approved both; a token another account approved, or one from a file that never recorded the account, is left valid, with a stderr note to revoke it on the Tokens page, so one person's login never withdraws another person's token. The file is read under the lock right before it is written, so a login that finished in another terminal meanwhile keeps its entry.

**The default login.** Any login made while no default is stored becomes the default (the first one, and also the first after a logout removed the default), and so does `--default`; a later login keeps the existing default and says `The default login stays space "X" at E; use --default to switch.` Whenever the default changes from one login to another, stderr says `The default login changed from ... to ....` Re-logging in to the default's own key keeps it the default. `--default` over a default another account approved needs the prompt's yes or `--force`, like a replacement.

**Logout.** `PrepareLogout` takes every login of `--bucket` (else the default login's space; no default is a refusal), narrowed to the logins issued by `--site` or `SLIVINGDOC_SITE` when either is set; none for the space is `ErrNoLogin`, and none left after that narrowing is `ErrNoLogin` naming the site filter. `Logout.Run` revokes each at its own `site`; a revoked token (204) or one the site no longer knows (401 `invalid_token`) is removed under the lock (`Logout.remove`), with one stdout line per removed login, and removing the default clears it. `Logout.remove` deletes an entry only while its stored token is still the one just revoked: a login another process stored for the same key after `PrepareLogout` read the file is kept, and stdout says `Revoked the token for space "X" at E; a newer login for it was kept`, so a logout never orphans a live token. A failed revocation keeps that login stored, prints no "revoked" line for it, and ends the command nonzero, so the logout can be repeated.

**Which storage a process uses.** `resolveStorage` runs first in `Flags.resolve`, for `serve`, `pull` and `commit` alike. In `auto` it collects the S3 signals (`s3Signals`), which decide whether a stored login applies: any of `awsSignals` that is set (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_REGION`, `AWS_DEFAULT_REGION`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_ROLE_ARN`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_S3`, `SLIVINGDOC_PATH_STYLE`), any `AWS_CONTAINER_CREDENTIALS_*` variable, the S3-only flags `--region` and `--path-style`, and an existing `~/.aws/credentials` or `~/.aws/config` (under `HOME`, or `USERPROFILE` on Windows). The precedence, exactly:

| `--storage` | `SLIVINGDOC_TOKEN` | Stored login for the space | Bucket | S3 signals | Result |
|---|---|---|---|---|---|
| `s3` | ignored | ignored (file never read) | explicit | used | S3 |
| `hosted` | set | any (the file is read only for the no-bucket fallback on a server without `GET /v1/token`) | any; none: the token's own space from `GET /v1/token`, or, on a server without it, the default login's space when that login is for the same endpoint, else a refusal asking for `--bucket` | ignored | hosted with the variable's token |
| `hosted` | unset | usable | any | ignored | hosted with the login's token, at its endpoint |
| `hosted` | unset | none, or not for this endpoint | any | ignored | refusal: run `slivingdoc login` |
| `auto` | set | any | any | `--endpoint` flag, `AWS_ENDPOINT_URL` or `AWS_ENDPOINT_URL_S3` | refusal naming them: pass `--storage hosted` or `--storage s3` |
| `auto` | set | any (the file is read only for the no-bucket fallback on a server without `GET /v1/token`) | any; none: the token's own space from `GET /v1/token`, or, on a server without it, the default login's space when that login is for the same endpoint, else a refusal asking for `--bucket` | none of those three (any other signal is ignored) | hosted with the variable's token |
| `auto` | unset | usable | from the default login | any | hosted with the login's token |
| `auto` | unset | usable | explicit (`--bucket` or `SLIVINGDOC_BUCKET`) | any | refusal naming them: pass `--storage hosted` or `--storage s3` |
| `auto` | unset | usable | explicit | none | hosted with the login's token |
| `auto` | unset | none, or not for this endpoint | any | any | S3 |
| `auto` or `hosted` | unset | several for the space at different endpoints, no explicit endpoint | any | any | refusal: pass `--endpoint` (also when the default names one of them) |

So the common case stays one command: after `slivingdoc login`, `slivingdoc serve` with no bucket uses the default login, whatever AWS configuration the machine has, because S3 has no bucket to use. A command line that names its bucket gets the login only when nothing on the machine configures S3; otherwise it must say which store it means. An expired login that would be used is a refusal (`Login.Usable`) naming the date, `run 'slivingdoc login --bucket <space>'` and `--storage s3`; nothing is sent. Outside `s3`, with no `SLIVINGDOC_TOKEN`, an omitted `--bucket` (and `SLIVINGDOC_BUCKET`) is the default login's space, but only when the outcome is hosted: when the login does not apply (another explicit endpoint) the process falls back to S3 with no bucket, which is the usual `bucket is required` refusal, never an S3 bucket named after the space. The variable's token keeps the endpoint rule (`--endpoint`, `SLIVINGDOC_ENDPOINT`, `DefaultHostedEndpoint`); it never borrows a login's endpoint. The variable's token is refused in `auto` only beside a setting that points S3 at a host (`tokenDestinations`: the `--endpoint` flag and `destinationSignals`, `AWS_ENDPOINT_URL` and `AWS_ENDPOINT_URL_S3`). This is an intent check, not a leak guard: hosted mode never reads the two variables, so the token cannot follow them, but an S3 host configured on purpose beside a token is a guess `auto` will not make; `--storage hosted` sends the token only to the hosted endpoint. A region, AWS credentials, a profile or the `~/.aws` files are no refusal (a profile may carry an `endpoint_url`, but hosted mode reads none of them), so `SLIVINGDOC_TOKEN` with `serve --bucket` works on a machine that also uses AWS. `SLIVINGDOC_ENDPOINT` names the hosted API and is no refusal. At startup `logStorage` records the outcome at Info: `storage selected backend=s3|hosted endpoint=<url or aws-default> space=<bucket, or "the token's own" before the lookup> token=none|env|login`, never the token; an S3 process with no endpoint of its own (an explicitly empty `--endpoint` included) logs the variable the SDK will read, `AWS_ENDPOINT_URL_S3` before `AWS_ENDPOINT_URL`, as `<scheme>://<host> (<name>)` (`endpointForLog`: scheme, host and port only, with no user information, path or IPv6 zone; a value without a scheme or a host is `an unparsable URL`), and otherwise `aws-default (SDK: env or profile)`, because a shared profile's `endpoint_url` may still redirect the SDK.

**The space a hosted process uses.** Every hosted process asks the API which space its token reaches before it builds the store (`resolveHostedSpace` over `httpstore.DescribeToken`, [hosted-mode.md](./hosted-mode.md)), and never picks between two answers silently. The token alone is enough: the variable's token with no `--bucket` or `SLIVINGDOC_BUCKET` uses the token's own space, whatever login is stored, and that path never reads the credentials file, so a broken or foreign file never stops a token user. Otherwise the bucket must be the token's space, and the refusal names the fix for where the bucket came from (`config.bucketFrom`, `spaceMismatch`): a stored login whose token reaches another space (the space was renamed or the token re-issued on the site) says to run `slivingdoc login --bucket <space>` again; a bucket from `--bucket` says to drop `--bucket` or use a token made for it; a bucket from `SLIVINGDOC_BUCKET` says to unset `SLIVINGDOC_BUCKET` or use a token made for it. A server without `GET /v1/token` keeps a given bucket, which the access check then proves; with none, the variable's token falls back to the default login's space only when that login was issued for the endpoint the token goes to (`defaultLoginSpace`, which reads the file only then), and otherwise refuses asking for `--bucket`, naming the default login's endpoint when that is why. `setup` logs the space it settled on once (`hosted space resolved`). `login` itself does not call `DescribeToken`: the site's token answer names the space and access, `Login.accept` checks them against what was asked, and the first process that uses the login checks the space against the API.

**A stored token only reaches its own endpoint.** With no explicit endpoint, `Set.ForSpace` picks the only login for the space; several at different endpoints are a refusal asking for `--endpoint`, even when the default names one of them, so a second login never silently redirects a command line that named only the space. An explicit `--endpoint` or `SLIVINGDOC_ENDPOINT` selects exactly the login issued for it (`Set.Lookup`, after `normalizeEndpoint`), so a different endpoint means the login does not apply: S3 under `auto`, a refusal naming the endpoint the login was issued for under `hosted`. `--storage s3` never reads the token or the file, and in `auto` an `--endpoint` flag, `AWS_ENDPOINT_URL` or `AWS_ENDPOINT_URL_S3` beside `SLIVINGDOC_TOKEN` is a refusal, which closes the old gotcha of an S3 `--endpoint` receiving a stray `SLIVINGDOC_TOKEN` ([hosted-mode.md](./hosted-mode.md)).

**The credentials file at startup.** Outside `s3` mode, a process without `SLIVINGDOC_TOKEN` reads the file (`loadLogins`) in `resolveStorage`; a process with it reads the file only for the old-server fallback above (`defaultLoginSpace`), when no bucket is given. No configuration directory in the environment means no logins. `loadLogins` returns the bare error for a file that exists but cannot be read, and each caller words the fix: `resolveStorage` refuses startup naming the file and suggesting `fix or remove it, or pass --storage s3`; the fallback refuses with `app: hosted storage cannot name the token's space, and no default login names one; pass the space name as --bucket or SLIVINGDOC_BUCKET`, `app: hosted storage cannot name the token's space, and the default login is for <endpoint>, not <endpoint>; pass the space name as --bucket or SLIVINGDOC_BUCKET`, or, for a credentials file that cannot be read, `app: hosted storage cannot name the token's space, and the stored logins cannot supply it: <redacted cause>; fix or remove the credentials file, or pass the space name as --bucket or SLIVINGDOC_BUCKET` (a `redactedError` that still matches `credentials.ErrMalformed` or `credentials.ErrExposed` through `errors.Is`, never the raw cause). `version` and `-h` exit before `Setup`, so they never read it.

**Refused tokens.** When the hosted startup check refuses a token that came from a stored login (`config.tokenOrigin` is `originLogin`), `checkStore` says `app: hosted storage refused the stored login: ...; run 'slivingdoc login' again, or check --bucket` instead of naming `SLIVINGDOC_TOKEN`. A token revoked while `serve` runs is still reported by the notebook's fixed `ACCESS_DENIED` message, which names `SLIVINGDOC_TOKEN`: the notebook does not know where its token came from ([errors.md](./errors.md)).

## Threat model

**Assets.** The hosted API token (bearer access to one space, read and write or read only, until its expiry); the user code and device code of an open approval; the credentials file and its default; the notebook content a token can read or overwrite; and the choice of store, which decides where a process sends notes and credentials.

**Actors.** The person running `login` (trusted, but can be rushed or phished); another person who sees or is sent the user code or the approval page; another local user on the same machine; a malicious or compromised site, or a site reached through a mistaken `--site` or `SLIVINGDOC_SITE`; a network attacker (confined by TLS to what a site or endpoint answers); and an operator whose machine carries both AWS configuration and a stored login.

**Trust boundaries.** The site's answers (start, token, revoke) are untrusted input until validated. The browser is outside the process: the client only opens a page it built. The credentials file and its directory are trusted only when the effective user owns them and nobody else can write them. The environment and flags are the operator's, but a stray variable is not proof of intent. The hosted endpoint receives the token and is trusted only when the login for it was issued for it.

| Threat | Mitigation |
|---|---|
| Someone else approves the code first (a phished or shoulder-surfed code), so the victim stores the attacker's token, or replaces their own login with it | `approvedBy` shows approver, owner, space, access, endpoint and site before anything is stored; a terminal asks `Store this login? [y/N]` and revokes on anything but yes, an interrupt included; without a terminal a login or `--default` over another account's entry is refused and revoked unless `--force`; the result line names the approver; a login made while no default is stored becomes the default, so the result line and the `default` stderr lines are what show it |
| A login replaces and revokes another person's valid token | `Login.report` revokes a replaced token only when the same account approved both; otherwise it prints a note |
| A mistaken or hostile `--site` / `SLIVINGDOC_SITE` mints a token for its own endpoint, then replaces or revokes a real login | stderr names a non-default site and its source before `start`; `DefaultSite` must issue for `DefaultHostedEndpoint`; a login from one site never replaces or revokes an entry another site issued (`log out of that login first`); the result line names a non-default endpoint |
| The site answers a page on another host, a `file:` URL, or a code carrying terminal escapes | the client builds both pages from the site origin, puts the code in the fragment, requires `verificationUriComplete` to match, and requires the consonant code shape |
| The site answers a token for another space or with write access for `--read-only` | `Login.accept` refuses and revokes |
| A site makes the client poll hard, wait for hours, or read unbounded answers | interval default 5 s and floor 1 s, `expiresIn` capped at 1800 s, answers read up to 16 KiB, requests under 4 KiB |
| A token is minted but lost (broken, oversize or undecodable answer, cancellation mid-poll, an unanswered poll before the code expired, a refused answer, an interrupt at the prompt) | a sendable token is revoked (`Login.discard`, on `revocationContext` so an interrupt does not skip it); otherwise the error carries `TokenHint` |
| `logout` believes a token is revoked when it is not, or removes a newer login | only 204 or 401 `invalid_token` count as revoked; anything else keeps the entry and exits nonzero; an entry whose token changed since the logout read it is kept |
| Another local user reads the tokens or plants their own login | ownership and mode checks on the file and directory, `O_NOFOLLOW` and a symbolic link refusal, regular files only, 1 MiB bound, `0600`/`0700` on write |
| Two logins or a login and a logout interleave and lose an entry | `File.Lock` around load, change and save |
| A stored login silently turns an S3 command line hosted, sending notes to the wrong store | in `auto` an explicit bucket plus any S3 signal is a refusal; only a bucket taken from the default login, or `--storage hosted`, picks the login over S3 configuration; `logStorage` records the outcome |
| A stray `SLIVINGDOC_TOKEN` goes to a host the operator meant for S3 | hosted mode reads only `--endpoint`, `SLIVINGDOC_ENDPOINT` or the default, never the AWS endpoint variables; in `auto` the token beside the `--endpoint` flag, `AWS_ENDPOINT_URL` or `AWS_ENDPOINT_URL_S3` is a refusal (an intent check), and `--storage hosted` states the intent |
| A space with logins at two endpoints resolves to the wrong one | `ForSpace` refuses as ambiguous even when the default names one |

**Residual risks.**

- A person at a terminal who answers `y` without reading the approval, or a script that passes `--force`, accepts another account's approval.
- Without a terminal nobody confirms the approver: a first login, or one for a key no other account's login holds, is stored on the approval alone, and a login made while no default is stored becomes the default. Requiring `--force` for every such login was considered and not done: an agent or script running `login` would pass it every time, which adds a step but no check. `approvedBy` on stderr and the result line naming the approver are what a script can check.
- On Windows the credentials file has no owner or mode check and no `O_NOFOLLOW`: it relies on the ACLs of the user profile (`AppData`) that `Locate` places it in, and on `Load`'s `Lstat` check against a symbolic link, which a swap between the check and the open could defeat. An owner-only DACL was not implemented: it needs the Windows security API and a Windows host to test it, neither of which the gate has.
- Ancestors of the configuration directory are not checked; a directory another user can write above it could replace it.
- An S3 setup that uses none of the listed signals (an EC2 instance role through instance metadata, with the default region) is invisible to `s3Signals`: an explicit bucket that matches a stored login goes hosted. The Info record and `--storage s3` are the remedies.
- A process reads the file without the lock, so it can read the file an instant before a concurrent login replaces it; it then uses the older token, which stays valid unless the same account's login revoked it.
- The site itself is trusted to issue tokens only for the approving account's spaces and to report `account` and `owner` truthfully; a compromised default site can still mint tokens for the default endpoint.
- The user code is shown on stderr and in the browser's address bar fragment; anyone who reads it within its lifetime can approve it first, which the confirmation above mitigates but cannot prevent.

## Gotchas

- The token is read once at startup; after a new login, an MCP host must restart `serve`.
- A space renamed on the site keeps its old name in the file; the gateway answers `no_space` and the startup check says to log in again.
- The file is read through the injected environment (`ProcessOptions.Env`), never `os.UserConfigDir`, so tests stay hermetic: `internal/integrationtest` drops `SLIVINGDOC_CONFIG_DIR`, `SLIVINGDOC_STORAGE`, `SLIVINGDOC_SITE`, `SLIVINGDOC_TOKEN` and `SLIVINGDOC_ENDPOINT` (`sanitizedEnv`) and gives every helper its own empty `SLIVINGDOC_CONFIG_DIR`; the `internal/app` process helper drops the same names and every name it sets itself (`helperEnv`) before appending its own values, so the child sees each name once; `release_test.go` drops them and points every binary at a per-run empty directory made in `TestMain`; and `testProcess` passes no `HOME`.
- Tests that write a credentials file create its directory `0700` themselves (a `cfg` subdirectory of `t.TempDir()`): under a `0002` umask a bare `t.TempDir()` is group-writable, which `ErrExposed` refuses.
- `os/exec` is banned module-wide (`TestNoGitExecutableOrGit2goImport`), so the browser opener finds and starts its program with `os.StartProcess`.
- The integration helper takes the operating system's signals only when `SLIVINGDOC_INTEGRATION_OS_SIGNALS` is set (`helperSignalsEnv`), for the interrupt scenario; and `SLIVINGDOC_INTEGRATION_SITE_ROUTE` (`helperSiteRouteEnv`) sends every site request to a reference site through `ProcessOptions.SiteClient` (`routedSite`), so the default site's endpoint rule runs black box against `sitetest.SetOrigin(DefaultSite)`.
- The integration helper's `Sleep` waits a hundredth of what the site asks for; exact poll timing is pinned by the `sitelogin` unit tests over a fake clock, not by the scenarios.
- Scenario helpers run on pipes, so they are never on a terminal: the prompt is covered by `internal/app` unit tests through `ProcessOptions.Terminal` and `Stdin`. Each helper also gets an empty `HOME` (`spawnHelperIn`), because a developer's `~/.aws` files are an S3 signal.
- `Set.Put` returns `ErrNoLogin` when nothing was replaced: absence is an error by the code style, so callers test `err == nil` for "a login was replaced". It never sets the default; `Set.SetDefault` does.
- CI keeps using `SLIVINGDOC_TOKEN`; the login is for people.
