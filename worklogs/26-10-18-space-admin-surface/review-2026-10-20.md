## Finding 1: phantom S3 groups and duplicated directories (behavior, major)

`TestSpaceS3Directories` only asserts the first group. The actual output of
that test is:

```text
S3  endpoint=(AWS)  region=eu-north-1  profile=dev  key=...
  analytics (/a, /b)
  team

S3  endpoint=(AWS)  region=us-east-1  profile=(ambient)  key=...
 ! analytics (/b)

S3  endpoint=https://other.example.test  region=us-east-1  profile=(ambient)  key=...
 ! analytics (/b, /c)
 ! team (/d)

S3  endpoint=(AWS)  region=us-east-1  profile=prod  key=...
 ! analytics (/b)
 ! team (/e)
```

Two defects produce this:

1. `Space.prepare` appends a recorded identity before it dedupes by the
   resolved store key. A record whose fields are empty resolves to the
   ambient chain and becomes an extra group even when the current group is
   the same identity.
2. `s3Space.matches` uses `recordedField`, which treats an empty recorded
   endpoint, region, or profile as a wildcard. The README's data model says
   an empty endpoint means the provider default and an empty profile means
   the ambient chain, not "unpinned". The wildcard makes one directory
   record decorate several identities, so `/b` appears in four groups.

Recommended fix:

- compare the recorded target with the identity exactly after normalizing an
  empty region to `s3store.DefaultRegion`; empty endpoint and profile remain
  meaningful values;
- build each recorded identity, then dedupe on `backend.key` before
  appending it, so two raw keys that resolve to one identity produce one
  group;
- rewrite `TestSpaceS3Directories` to assert the complete output, not only
  the first group, and add a case for a partial record.

This contradicts the phase-6 sentence "match ... every non-empty record
field". The next session must record the chosen semantics in
`architecture/decisions.md` and in the phase-6 documentation, and update the
test in the same change.

## Finding 2: `spaceHelp` promises S3 default resolution that does not exist

`cmd/login/login.go` says a stored default is what "serve, pull and commit
use when neither --space nor SLIVINGDOC_SPACE is given", and that an S3
target is stored "so serve, pull and commit reach the same bucket".

In this build `resolveStorage` returns an S3 selection from `--bucket` /
`SLIVINGDOC_BUCKET` only; it never reads `settings.defaults`. S3 default
resolution is the sibling worklog's phase 2. The help text must say that the
stored S3 default is recorded for that later lookup, or speak only about the
hosted default.

## Finding 3: architecture prose says `space` reads settings only for directories

`architecture/config.md` (the key-files row, the settings table row, and the
"remembered notebook" paragraph) and `architecture/decisions.md` decision 49
say `space` uses the settings file only for the directory column.
`hostedSpace.Default` and `s3Space.Default` also read `defaults` to mark the
default, synthesize an unlisted default, and decide the no-default hint.
The invariant "a record never chooses the command's own target" stays true;
the "only directories" wording must be widened.

## Finding 4: `running.md` command table understates `space`

`architecture/running.md` says `space` lists "every stored login's spaces".
It now lists S3 buckets too. Add the S3 surface and point at the S3 default
rule in `login.md`.

## Finding 5: stale shared-interface signature

The README's `spaceBackend` shows
`SetDefault(ctx context.Context, t settings.Target) error`; the code and
`architecture/login.md` use `SetDefault(ctx context.Context, name string)`.
Phase 6's decision 4 records the change. Update the README shared interface
and the phase-4 snippet so a reader does not implement the old signature.

## Finding 6: `present.go` preamble is false for `space`

The file comment says the plain renderings are what the commands printed
before they had a styled form, "so scripts see no change". The workspace
plain listing is new in this worklog. Limit the sentence to the login and
logout renderings.

## Finding 7: path style is lost for a custom endpoint on a degraded identity

`s3Space.pathStyleFor` returns `h.resolved.PathStyle` or the dotted-name
rule. A recorded identity whose `Resolve` or `Identity` failed keeps a zero
`Resolved`, so selecting its row in the picker stores `pathStyle=false` even
when `h.header.Endpoint` is a custom endpoint, where path style is always
required. Simplest rule:

```go
return h.resolved.PathStyle || h.header.Endpoint != "" || strings.Contains(name, ".")
```

Add a test with a custom recorded endpoint and a failed identity. This is
only reachable through the picker today, because `space <name>` skips
unreachable rows.

## Finding 8: unreachable rows are selectable only through the picker

`space <name>` refuses a target no reachable listing returned, while the
picker lets the person choose an unreachable `!` row and stores it as the
default. Decide whether that is intended. If not, treat an unreachable pick
like the non-interactive refusal.

## Finding 9: the backend `Default` error is ignored

`Space.listing` calls `def, _, _ := backend.Default(ctx)`. Both backends
cannot fail, and the README interface returns an error. Either propagate the
error or remove it from the interface and the implementations. Do not leave
the discard in place.

## Finding 10: auto-mode explicit identity wording

`Space.resolveBackends` treats `AWS_PROFILE`, `AWS_REGION`, an AWS endpoint
variable, and an S3 flag as selecting an *explicit* S3 identity, so a failure
to resolve it refuses the command and hides hosted groups. The README says
"a backend that `auto` tried reports its hint and does not hide the others".
Every one of those variables is an auto signal, not `--storage s3`. Decide
whether an environment-selected identity should degrade or refuse, and make
the README and the code agree.

## Resolution (2026-10-20, session 10)

Worker: review-remediation agent. Decision 54 in

| Finding | Resolution |
| --- | --- |
| 1. Phantom groups and duplicated directories | `s3Space.matches` compares `{endpoint, region, profile}` exactly, normalizing an empty region to `us-east-1`; an empty endpoint and profile are values. `Space.prepare` dedupes on the resolved `backend.key`. `TestSpaceS3Directories` asserts the full stdout and stderr, including a partial-record case. |
| 2. `spaceHelp` over-promises S3 defaults | It names the hosted default as what `serve`, `pull` and `commit` use and says only that an S3 default is stored under the identity's store key. |
| 3. Settings prose says directories only | `architecture/config.md` (key-files row, settings row, remembered-notebook paragraph) and decision 49 now include the S3 defaults `space` marks. |
| 4. `running.md` understates `space` | The command table and the `space` section name S3 listing, create, default and the `!` rows. |
| 5. Stale interface signature | The README and phase-4 snippets show `Default() (settings.Target, bool)` and `SetDefault(ctx, name)`. |
| 6. `present.go` preamble | The no-change claim is limited to the login and logout renderings. |
| 7. Path style on a degraded custom endpoint | `pathStyleFor` returns true for any custom endpoint; `TestSpaceS3FailedIdentityKeepsCustomEndpointPathStyle` proves it. |
| 8. Unreachable rows selectable in the picker | An unreachable pick is refused through `Space.unreachableRefusal`, the same refusal `space <name>` gives; `TestSpacePickerRefusesUnreachable` proves the default is unchanged. |
| 9. Discarded `Default` error | The interface and both backends return `(settings.Target, bool)`; `Space.listing` no longer discards an error. |
| 10. Auto-mode explicit identity | Only `--storage s3` or a flag that names the identity is explicit and refuses; an environment-selected identity in `auto` degrades and keeps the other groups. `TestSpaceAutoS3IdentityFailureDegrades` covers the environment case; `TestSpaceS3UnknownProfile` still covers the flag case. |

The picker decision in finding 8 makes the degraded-selection path of finding 7
unreachable from the CLI, but the path-style rule stays correct and tested at
the backend boundary.
